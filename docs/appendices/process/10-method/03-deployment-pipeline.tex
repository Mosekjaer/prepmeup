In this appendix we describe what happens from a pull request is merged until the new version runs in production, and why we set it up this way. The daily rules for branches, commits and pull requests are in appendix 10.1, and the reasons for the technology choices are in appendix 2.1.

\section{Scope}
The system runs as one Docker Compose stack on our own server, managed by Coolify. The stack has the API, the SQL Server database, Keycloak and Keycloak's own PostgreSQL database. The customer app and the admin panel are not part of the pipeline yet. When they are added, it will be one more image to build and one more service in the compose file.

We have left out a staging environment, blue/green and canary releases, automatic rollback and monitoring. That is too much for a project that lasts one semester.

\section{From Push to Running Container}
Our pipeline is a GitHub Actions workflow. A workflow is made of jobs, and it starts when something happens in the repository, for example a push \cite{github-understanding-actions}. The steps are:

\begin{enumerate}
    \item A developer pushes a branch. The CI workflow builds the backend and the clients and runs all tests. A second workflow checks the branch name and the pull request title.
    \item The pull request can only be merged when the checks are green and another group member has reviewed it.
    \item After the squash merge, the CI workflow runs again on the main branch.
    \item If build and tests are green, the publish job builds the API image and the Keycloak image and pushes them to GitHub Container Registry (GHCR).
    \item If the publish job succeeded, the deploy job calls Coolify's deploy webhook. The job fails unless Coolify answers 200.
    \item Coolify fetches the production compose file from the repository, pulls the images and starts the stack.
    \item Coolify calls the API's health endpoint. If it does not answer, the deployment is not marked as healthy.
\end{enumerate}

Every step depends on the one before it, so there is only one way from a commit to production, and it starts with the tests.

\section{Why GitHub Actions Decides When We Deploy}
Coolify can watch the repository itself and deploy on every push to the main branch. That is how we had it at first, and we turned it off.

The problem was that Coolify did not know anything about the tests. CI and Coolify both started from the same commit, but independently of each other, so a failed test run did not stop Coolify from building and starting the same code. In practice we had two ways into production, and only one of them ran the tests.

Fowler defines continuous integration as a practice where work is integrated at least daily and each integration is verified by an automated build that includes the tests \cite{fowler-continuous-integration}. If a deployment can skip that build, the tests do not protect production. So we moved the decision to the workflow that has the test result.

The deploy job needs the publish job, and the publish job needs the two test jobs. GitHub Actions skips a job when a job it needs has failed \cite{github-workflow-syntax}, so if a test fails, no image is built and the webhook is never called. Nobody has to remember not to deploy when the tests are red.

When the main branch is green, the deployment happens automatically, without anyone approving it. With GitHub Flow the main branch should always be deployable \cite{chacon-github-flow-2011}, and CI already knows more about the change than the person who would click the button, so an approval step would only add waiting time.

We also considered letting Coolify check the registry for new images. We chose the webhook, because the registry does not know if an image comes from a green run. With the webhook, deployment is the last step in the same chain as the tests.

\subsection*{A Bug in the First Deploy Job}
A green deploy job should mean that Coolify started a deployment. In the first version we called the webhook with curl and its fail option, which only counts 4xx and 5xx answers as errors. The webhook address was saved with http instead of https, so Cloudflare, which sits in front of the server, answered 301 to redirect to HTTPS. curl did not see that as an error, so the job was green even though nothing was deployed.

Now the job refuses to call an address that is not HTTPS, and it only passes if the answer is exactly 200. The answer is printed in the log, so we can see what Coolify or the proxy said. It also means the token is never sent over plain HTTP, even if the address is saved wrong again.

\section{Why CI Builds the Images}
The images are built once, by the publish job, and pushed to GHCR. Coolify only pulls them.

If Coolify built the image itself after CI had run, there would be two images: the one the tests ran against and the one the users get. They would be built from the same code, but at different times, and a base image can change between the two builds. Then the image in production has never been tested. When we build once and deploy that image, production runs exactly what the tests approved.

It also makes a rollback cheaper. If Coolify builds, there is no old image to go back to, so we would have to revert the commit and wait for a new build while production is down. With the images saved in a registry, a rollback is just choosing an older tag (section~\ref{sec:rollback}).

The cost is that CI has to log in to a registry and Coolify has to be able to pull from it. CI pushes with the token GitHub Actions creates for each run, so we do not store an extra password. Our packages on GHCR are public, so Coolify can pull without logging in. That is one secret less that can expire or be set up wrong. It does mean that anyone can download our images. We think that is fine, because the images do not contain any secrets (section~\ref{sec:secrets}). What can be downloaded is the compiled application, and it gives no access to our system.

We build the Keycloak image the same way, because it contains our realm file. That way a change to the login setup is reviewed in a pull request like any other change. Both images are built by the same job from the same commit, so they always get the same tag and move forward and back together.

\section{Why We Keep One Compose File}
In Coolify we could also create each container separately in the web interface. We keep the whole stack as one compose application, with the production compose file from the repository as the source. The only thing we changed is that the API and Keycloak are now pulled as images instead of being built by Coolify.

The compose file describes the network, the start order, the health checks, the volumes and which environment variables are needed. If we created the containers one by one in Coolify, all of that would only exist in a web interface. Nobody could review a change to it in a pull request or compare it with an earlier version, and we could not run the same setup locally. The compose file also matches the deployment view of our architecture (appendix 3.1), so the documentation and the running system stay the same.

Compose is also made for this. A multi-container application is defined in one YAML file \cite{docker-compose-overview}, and each service can be replaced independently of the others \cite{docker-compose-services}. Waiting for a database is done with a health check and a condition on the service that depends on it \cite{docker-compose-startup-order}. Our stack uses that for both databases.

The downside is that the stack is deployed as one unit, so we cannot scale one service on its own. We do not need that.

\section{Image Tags and Rollback}\label{sec:rollback}
\subsection{Two Tags}
Every image is pushed with two tags. The first is the commit SHA. It points to one image built from one commit, and it never changes. The second is called main, and it always points to the newest image built from a green main branch. This is the tag the compose file uses by default.

We need both because they answer different questions. What production should run right now is answered by a tag that moves by itself. Which image something exactly is can only be answered by a tag that never moves.

The moving tag has a weakness. If two pull requests are merged shortly after each other, both publish jobs write the main tag, and the one that finishes last wins. That is not necessarily the newest commit. The SHA tag does not have that problem, so when we check what is running or roll back, we always use the SHA.

The compose file reads the tag from a variable:

\begin{lstlisting}
image: "ghcr.io/mosekjaer/prepmeup-api:${PMU_IMAGE_TAG:-main}"
pull_policy: always
\end{lstlisting}

If the variable is not set, the stack runs the main tag. If it is set, the stack is locked to that build. The pull policy makes sure the image is fetched again when we redeploy, also when the tag has the same name as before.

\subsection{How to Roll Back}
We wrote the steps down, so nobody has to figure them out while production is down.

\begin{enumerate}
    \item Find the SHA that worked. Under Actions on GitHub, find the last run on the main branch that deployed without problems, which is the run before the one that broke production, and copy the full commit SHA. The package page on GitHub also lists all tags with a timestamp.
    \item In Coolify, open the PrepMeUp resource and set the environment variable PMU\_IMAGE\_TAG to that SHA. Use the full SHA and not main.
    \item Press Deploy. Coolify pulls the two images with that tag and restarts the stack, so the API and Keycloak go back together.
    \item Check that it works. The health endpoint must answer 200 and Healthy. Then log in through the app, because the API can be healthy while Keycloak is broken.
    \item Fix the bug on a normal branch. The rollback did not change anything in git, so the main branch is left alone.
    \item When the fix is merged and the main branch is green, delete the variable in Coolify and redeploy. If we forget this, production stays on the old image while all workflows are green.
\end{enumerate}

The rollback takes seconds and needs no build and no commit. It does not roll back the database, see section~\ref{sec:migrations}.

\section{Secrets}\label{sec:secrets}
The production passwords and keys are only in one place, the environment variables in Coolify. They are not in the repository, the compose file or the images, and the AI tools cannot read them. Secrets should not be stored in source code or deployed with the app, and environment variables are one way to keep them out of both \cite{microsoft-aspnetcore-app-secrets}. De Sanctis does the same with a settings file that is created directly on the production server \cite[sec.~12.1.4]{desanctis-web-apis-aspnet-core}.

GitHub stores two secrets for the pipeline: the address of Coolify's deploy webhook and a Coolify API token that is sent with the call. The token can only start a deployment. It cannot read the environment variables, so if it leaks, nobody gets a database password. The images are pushed with the token GitHub Actions creates for each run, so there is no long-lived registry password that can leak.

In the compose file every secret is written like this:

\begin{lstlisting}
Password=${MSSQL_SA_PASSWORD:?set MSSQL_SA_PASSWORD}
\end{lstlisting}

The part with the question mark matters for security. Without it, a missing variable becomes an empty text and the stack starts anyway with an empty password, and it would look like it works. With it, Compose refuses to start and prints which variable is missing \cite{docker-compose-interpolation}. The compose file also works as a list of the values the server needs, without any of them being written down.

\section{Database Migrations}\label{sec:migrations}
Changes to the database schema are run as a separate step before the API starts. The API does not run them itself at startup.

The database cannot be reached from outside the Docker network, so we cannot run the EF Core update command from GitHub Actions. Instead the migrations are packed as a migration bundle. It is a program that can run without the .NET SDK and the EF Core tools, and it is one of the two approaches De Sanctis recommends for getting a schema to production \cite[sec.~12.4.4]{desanctis-web-apis-aspnet-core}. The bundle runs as its own service inside the network, and the API waits for it:

\begin{lstlisting}
depends_on:
  migrator:
    condition: service_completed_successfully
\end{lstlisting}

If a migration fails, the deployment stops and the API does not start against a schema it does not match. If the API ran the migrations itself at startup, a failed migration would show up as errors in the application instead of as a failed deployment.

\subsection*{Schema Changes Must Work with the Previous Release}
A rollback changes which image runs, but it does not change the database. If a deployment changed the schema and then failed, a rollback gives us old code on a new schema.

So every schema change has to work with the previous release too. In practice a column is added before it is used and removed one release after we stopped using it. A rename is done as add, copy and later remove. A column is not made required in the same release that starts writing to it. It takes an extra release to remove something, but without the rule a rollback is only safe when the release had no migration, and we would not know which case we were in while production was down.

The migrator service cannot be made before we have a DbContext and a first migration. Until then this section describes what we have decided, and the implementation is its own task.

\section{Setup Outside the Repository}
Some parts of the pipeline cannot be created from the repository, so a clone is not enough to get a working deployment. We list them here so someone else can set it up again.

\begin{itemize}
    \item The two GHCR packages, prepmeup-api and prepmeup-keycloak, must exist and be public before the compose file uses them. A new package is private by default. If this is forgotten, CI and the webhook are green, and the error only shows up in Coolify's deployment log as denied or manifest unknown. It can be checked with docker pull from a machine that is not logged in to GitHub.
    \item Automatic deployment on git push must be turned off in Coolify. Otherwise Coolify still builds on every push to the main branch, and our gate does nothing. It can be tested by pushing a commit that only changes documentation and checking that Coolify does not deploy before the webhook is called.
    \item The webhook address and an API token with only the deploy permission must be saved as repository secrets on GitHub, with the names COOLIFY\_DEPLOY\_WEBHOOK and COOLIFY\_API\_TOKEN. The address must start with https. All variables the compose file marks as required must be set in Coolify.
    \item The health check on the API's health endpoint is set up in Coolify. It cannot be a health check in the compose file, because the ASP.NET image has neither curl nor wget.
    \item The main branch must be protected on GitHub: the build, test and conventions checks are required, one review is needed, and nobody can push directly. Without it the whole pipeline can be skipped with a push to the main branch. The local git hooks do not prevent that, because they run on the developer's own machine and can be skipped.
    \item Old GHCR packages and Coolify resources that are no longer used should be deleted, so there is only one place a deployment can come from.
\end{itemize}

\section{The Course and Our Choice of Tools}
The principles in the pipeline are ones we know from the courses:
\begin{itemize}
    \item Continuous integration with one automated build that includes the tests and runs on every push to the mainline \cite{fowler-continuous-integration}.
    \item GitHub Flow with a main branch that is always deployable \cite{chacon-github-flow-2011} and review before merge \cite{github-docs-github-flow}.
    \item A multi-container application defined in one compose file \cite{docker-compose-overview} with health checks and start conditions \cite{docker-compose-startup-order}.
    \item Production settings that only exist on the production server \cite[sec.~12.1.4]{desanctis-web-apis-aspnet-core} and configuration that depends on the environment \cite[sec.~2.4.2]{desanctis-web-apis-aspnet-core}.
    \item Migration bundles for schema changes \cite[sec.~12.4.4]{desanctis-web-apis-aspnet-core}.
\end{itemize}

The tools are different from the course. The course teaches CI with GitLab CI and deployment to a virtual machine in Azure. We use GitHub Actions, GHCR and Coolify on our own server. The repository is already on GitHub, so CI, the registry and the permissions are in the same place, and we do not have to move passwords between systems. Coolify runs a normal compose stack on a server we control, so production looks like what we run locally, and it is free.
