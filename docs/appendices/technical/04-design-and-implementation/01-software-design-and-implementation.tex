\section{Roles and Claims}
This section describes how the API tells a customer from an administrator (NFR-10). The login flow itself is in appendix 3.1.

\subsection{Realm Roles}
We have two roles, household and admin. The household role is for customers. It is still called household from before the requirements were changed (appendix 1.2). An admin is someone who works in the admin panel.

\subsubsection{How a User Gets a Role}
Every new user gets the household role automatically, and only an admin can give someone the admin role. So a customer only has the household role, while an admin has the household role \textit{and} the admin role.

We will create the first admin in the system by hand. After the release, new admins can only be added by an existing admin.

\subsubsection{Choice of Role Type}
Keycloak has two kinds of roles. A realm role belongs to the whole realm, so every app in it sees the same role. A client role belongs to one app only \cite{keycloak-server-admin-guide}.

We chose realm roles for two reasons. The roles say what a person is, not which app they are using. Also, the API does not need to know which app a token came from to decide if a request is allowed.

\subsubsection{Risk}
There is a risk we accept. Both apps are public clients, and their tokens are meant for the same API. A customer can therefore log in through the admin panel and get a valid token. What \textit{stops} them is the admin role, which the API checks on every admin endpoint. Without the role the API answers 403 (NFR-10). The admin panel should also send users without the role away, but that is only for the user's benefit. It is not what keeps the data safe.

\subsubsection{How the API Reads the Role}
Keycloak puts the realm roles in the token as a list called roles inside a claim called realm\_access. ASP.NET Core does not understand this format, so a check like ``is this user an admin'' would always fail. We therefore have a claims transformation in the API that runs on every authenticated request. It reads the list of roles from the realm\_access claim and adds each role as an ordinary role claim that ASP.NET Core understands. It skips roles the user already has, and it does nothing if the claim is missing or cannot be read.

After this, the controllers can protect an endpoint with the admin role in the normal ASP.NET Core way, without knowing anything about Keycloak's token format.

\subsection{Onboarding Status}
We store the onboarding status only in the database. So whenever the client needs to know if the user has finished onboarding, it has to ask the API.

This gives some extra calls to the database, which costs performance. We accept that. It fits clean architecture, because the data stays in the domain in the backend, and we avoid filling the token with information. That makes the system easier to maintain.

\section{Keycloak decisions}

\subsection{Login Library in the Admin Panel}
The admin panel logs in with react-oidc-context, which is built on oidc-client-ts. It follows the OpenID Connect standard and does not depend on Keycloak. The mobile app also uses standard OpenID Connect, so the two apps only differ in how they redirect and where they keep the token.

\subsection{Where the Admin Panel Keeps the Token}
The token is kept in memory only, so a script injected into the page cannot read it from browser storage. A reload loses the token. The admin panel then sends the user to Keycloak, which logs them in again without a password as long as the Keycloak session is alive.

\subsection{Where the Mobile App Keeps the Token}
On the phone we keep the refresh token in Expo SecureStore. On Android SecureStore stores the value in SharedPreferences, encrypted with a key from the Android Keystore. On iOS it stores the value with the Keychain services \cite{expo-securestore}. The key in the Android Keystore never enters the process of the app \cite{android-keystore}. The access token is only kept in memory. When the app starts, it uses the stored refresh token to get a new access token.

A browser has no such storage. A script running on the page can read everything in web storage \cite{owasp-html5-security}, and SecureStore itself is only available on Android and iOS \cite{expo-securestore}. For that reason the mobile app does not support web, and the admin panel keeps its token in memory only.

\subsection{How the Admin Panel Checks the Role}
After login the admin panel calls the admin ping endpoint. If the answer is 200, the user is let in. If it is 403, the admin panel shows a message that the account has no access. This way only the API knows the rule for who is an admin, and the admin panel does not have to decode the token.

\subsection{Sign-in Screen and Sign-out}
A user who is not logged in sees a sign-in screen with a sign-in button. Sign-out ends the Keycloak session, as in the mobile app, so a customer who is turned away can sign in with another account.

\subsection{Token Refresh}
Both apps use the refresh token to renew the access token shortly before it expires. The admin panel uses the automatic silent renew in react-oidc-context. If the renewal fails or the API answers 401, the user is sent to the sign-in screen. The mobile app sets its own timer. If the API answers 401, the app renews the token and sends the request once more. If the answer is still 401, the user is logged out.

\subsection{Tests of the Admin Login}
We test the admin login with Vitest and mock react-oidc-context and the network, like the mobile app does with expo-auth-session. The tests check that the token is sent to the API, that a 403 shows the message, and that sign-out ends the session. The flow against Keycloak itself is checked by hand.

\section{Saving Data}
This section shows how data travels from the customer app to the database. The example is the onboarding screen, where the customer saves a name and an address. It is the only place in the system where data is saved so far.

\drawiofig[\linewidth]{save-customer-flow}{Saving a customer's name and address, from the app through the layers of the API to the database.}{fig:save-customer-flow}

The numbers below match the arrows in Figure~\ref{fig:save-customer-flow}.

\paragraph{1 and 2. The app sends the data.} The customer types a name and an address and taps Save. The app sends both to the API as PUT /user through the generated API client, with the access token in the Authorization header. The login flow that gives the app the token is in appendix 3.1.

\paragraph{3. The Api layer checks the request.} Before the controller runs, ASP.NET Core checks the token and the request body. A missing or invalid token gives 401. An empty name or address, or one that is too long, gives 400. The controller then takes the user id from the token and calls the customer service. The id is never sent in the body, so a customer can only change their own data.

\paragraph{4. Find the customer.} The service asks the repository for the customer with that user id. The repository is an interface in the Application layer. The Infrastructure layer implements it with EF Core, which turns the call into a SELECT.

\paragraph{5. Create or update.} If no customer is found, the service creates a new customer. Otherwise it updates the name and address on the one it found. The rules for name and address live in the customer entity in the Domain layer, so they hold no matter who calls it. The Api layer checks the same limits first, so a bad request stops with 400 before it reaches the domain.

\paragraph{6. Save.} The service asks the repository to save. EF Core writes an INSERT for a new customer or an UPDATE for an existing one.

\paragraph{7. Answer.} The API answers 204 No Content. The app then goes back to the previous screen. If the request fails, the app shows an error and the customer can try again.

The admin panel does not save anything yet. Its only call is a check that the user is an admin, so there is no admin save flow to draw.

\section{Keycloak Login flow: Client and admin}

The flowdiagram below shows how login flows for both a regular customer and for an administrator.

\drawiofig[\linewidth]{keycloak-login-flowchart}{Login with Keycloak for the customer app and the admin panel. The numbers match the steps below.}{fig:keycloak-login-flowchart}

The diagram assumes that the user has opened the client app.
When the app starts, the client app fetches the URL to keycloak's login-page from Keycloak's discovery document \cite{openid-connect-discovery}.
\begin{enumerate}
    \item In Client, the User (either customer or admin) clicks 'Log in'
    \item Client generates PKCE-values and state and saves them locally. They are:
        \begin{itemize}
            \item code\_verifier: a random string that stays with the client. It is sent later.
            \item code\_challenge: a SHA-256-hash of the code\_verifier. It is sent in step 3.
            \item state: another random string. It is sent as it is in step 3 (non-hashed).
        \end{itemize}
    \item Client builds and opens the login-URL for Keycloaks /auth-endpoint. It attaches (among others) the following values:
        \begin{itemize}
            \item client\_id: a string that is either `prepmeup-mobile' (if login is requested from customer app) or `prepmeup-admin' (if login is requested from admin panel).
            \item redirect\_uri: The address that Keycloak should send the user \textit{back} to.
            \item code\_challenge and state (generated in step 2)
        \end{itemize}
    \item Keycloak shows the login page, \textit{if} client\_id and redirect\_uri are valid. Also, keycloak saves code\_challenge and state for later (see step 8), and displays it's own login page.
    \item User types email and password and clicks 'log in'.
    \item Keycloak checks the credentials: are they correct?
        \begin{itemize}
            \item No: Keycloak shows an error on the login page and user tries again.
            \item Yes: Keycloak looks up the users realm roles.It is 'household' for customers and 'admin' for administrators. In step 12, these roles into the jwt token.
        \end{itemize}
    \item Keycloak does two things:
        \begin{itemize}
            \item starts a an SSO-session by putting an SSO-cookie in the browser, so that the user is logged in \textit{at keycloak}. As long as the SSO session is up, Keycloak will supply a new access token on a refresh token. The purpose of this, is then the user doesn't have to re-login everytime the jwt token expires.
            \item generates a random and short-lived authorization code. It is used in step 10 to exhange for an access token. This authorization code is bound to the client\_id, redirect\_uri and code\_challenge that client sent along in the URL in step 3.
        \end{itemize}
    \item On this step, something happens first on Keycloak-side and then on Client-side:
        \begin{itemize}
            \item Keycloak sends the browser back to redirect\_uri, which was provided by client in url in step 3. It sends back the authorization code and also the state back, which client provided in step 3.
            \item Client recieves the redirect with a state value and the authoriation code.
        \end{itemize}
    \item Client checks that state is the same as what was sent to Keycloak in step 3. This is how the client can tell that the response actually came from Keycloak and not some hacker.
        \begin{itemize}
            \item No: The login-process is stopped and the client doesn't ask keycloak for access token.
            \item Yes: Client continues to step 10.
        \end{itemize}
    \item Client sends a POST http request to Keycloaks token-endpoint. The request contains:
        \begin{itemize}
            \item grant\_type=authorization\_code: This tells keycloak that client would like to exchange \textit{some} code to \textit{some} token.
            \item code: The authorization code. This was recieved from Keycloak in step 9.
            \item code\_verifier: The secret string from step 2 (un-hashed).
            \item same client\_id and redirect\_uri as in step 3.
        \end{itemize}
    \item Keycloak checks the following:
        \begin{itemize}
            \item Is the authorization code even valid? As in unused and not expired?
            \item Are client\_id and redirect\_id the same as in step 3?
            \item Makes a PKCE-check: Keycloak hashes code\_verifier with the SHA-256 algorithm and compares it to code\_challenge, which it saved in step 4. If a hacker has somehow gotten hold of the authorization code in step 8 their request will fail here, because they have at most the code\_challenge, which was the hashed version of code\_verifier, and you cannot calculate backwards from SHA-256-hash \cite[sec.~1]{nist-fips-180-4}.
        \end{itemize}
        Is the request valid?
        \begin{itemize}
            \item No: Keycloak answers client with 400 Bad Request with the error invalid\_grant. The authorization code cannot be reused.
            \item Yes: Keycloak moves on to issue tokens in step 12.
        \end{itemize}
    \item Keycloak issues \textit{three} tokens:
        \begin{itemize}
            \item Access token of type jwt "Json Web Token" signed by keycloak. It contains bl.a. the users UUID, realm-roles (household and/or admin) and \textit{audience} (which is prepmeup-api). This jwt is valid for 15 minutes.
            \item Refresh token, which client can use to get a new access token, when the old one expires \textit{without} having to log in again. This, however, is only possible as long as the SSO-session (started in step 7) lives.
            \item ID token, which tells the client who is logged in. This info is only  used for logout.
        \end{itemize}
    \item Client stores the three recieved tokens in a way that depends if it's mobile-app (for customer) or admin-panel.
    Then the Client registers a function with the api-client that returns the current access token. The effect of this, is that before every request the api-client calls that function and can therefore add a non-expired token to the http request.
        \begin{itemize}
            \item admin-panel: All threee tokens are kept in the browsers memory and are lost when the page is reloaded. Admin has to click 'log in' again.
            \item mobile-app: access token and ID token are kept in memory and are lost when the app is closed. The refresh token is saved to persistent storage on the phone, so the user stays signed in when reopening the app.
        \end{itemize}
    \item User is now logged in.
\end{enumerate}

\section{Onboarding Flow: Customer}\label{sec:onboarding-customer}
This section shows what happens the first time a new customer uses the app. It starts when the customer creates an account in Keycloak and ends when their name and address are saved in our database (FR-01). In the requirements specification, onboarding is the step after the first login where the customer enters name and address (appendix 1.2).

\drawiofig[\linewidth]{onboarding-customer}{Onboarding of a new customer, from registration in Keycloak to saved name and address.}{fig:onboarding-customer}

Figure~\ref{fig:onboarding-customer} has four lanes: the customer app, Keycloak, the Web API and the database. The flow has six parts.

\paragraph{1. Sign in.} The customer opens the app and taps Sign in. The app has no login form of its own. It opens Keycloak's login page in the browser, in the same way as in Figure~\ref{fig:keycloak-login-flowchart}.

\paragraph{2. Create the account in Keycloak.} At the bottom of the login page there is a link, New user? Register. The customer taps it, fills in email, name and a password, and sends the form. Keycloak checks the input and creates the account. We have turned on registration in the realm, and the email is used as the username. Every new user gets the household role automatically (see Realm Roles). Keycloak then logs the customer in right away and sends the browser back to the app with an authorization code. The app exchanges the code for tokens as described in the login flow above.

At this point the customer exists in Keycloak, but the API does not know them yet. Keycloak only knows how to log them in. The name and address belong to our domain, so they are stored in our own database.

\paragraph{3. Ask the API for the profile.} The home screen calls GET /user with the access token. The API reads the user id from the token and asks the customer service for the customer with that id. The repository looks the customer up in the database. For a new customer nothing is found, and the API answers 404 Not Found.

For the app, this 404 is not an error. It means that the customer has not finished onboarding. This is how we read the onboarding status, as described in Onboarding Status: we do not keep a flag in the token, we ask the database. If the call fails for another reason, the home screen shows an error and a button to try again.

\paragraph{4. Fill in name and address.} When the app gets the 404, it opens the onboarding screen. The customer types a name and an address and taps Save. The button is disabled while the request is running, so the customer cannot send it twice.

\paragraph{5. Save.} The app sends the name and address to the API as PUT /user. The steps through the layers of the API are described in the Saving Data section and Figure~\ref{fig:save-customer-flow}. For a new customer the service creates a new customer, EF Core writes an INSERT, and the API answers 204 No Content.

\paragraph{6. Back to the home screen.} The app goes back to the home screen. The home screen loads the profile every time it is shown, so it calls GET /user again. This time the customer is found, the API answers 200 OK with the name and address, and the home screen welcomes the customer. Onboarding is done.

The next time the customer opens the app, GET /user answers 200 right away, and the onboarding screen is not shown. If the customer leaves the onboarding screen or closes the app before they save, the API still answers 404 the next time the home screen is shown, and the app opens the onboarding screen again. So a customer cannot use the app without a name and address.

\section{Zombie Users}\label{sec:zombie-users}
A zombie user is a user who exists in Keycloak but not in PrepMeUp. The user has an account and can log in, but our database has no customer for that user. This section describes how that happens, what it means for the system, what we could do about it, and why we do not handle it in this version.

\subsection{How a Zombie User Comes About}
The account and the customer are created in two different places, as the customer onboarding flow shows (Figure~\ref{fig:onboarding-customer}). Keycloak creates the account in part 2, but our database only gets a customer in part 5, when the customer saves name and address. If the flow stops anywhere between those two parts, we have a zombie user. That happens in three ways:
\begin{itemize}
  \item A customer registers but closes the app before saving name and address.
  \item Somebody registers on Keycloak's login page without ever using the app. The page is public, because Keycloak runs on a public server.
  \item The database is recreated, for example during development. The accounts in Keycloak are still there, but none of them have a customer any more.
\end{itemize}

An administrator can never be a zombie user in this sense. As the next section describes, an administrator has no customer in our database at all, because everything the API needs to know about them is in the token.

\subsection{What It Means for the System}
A zombie user cannot see or change anything that belongs to somebody else. The API finds the customer from the user id in the token, and a zombie user has no customer, so the API answers 404 when the app asks for the profile. The app reads that as ``onboarding is not done'' and opens the onboarding screen, as in part 3 of the onboarding flow. So a customer who stopped halfway just continues the next time they open the app.

The real problem is the accounts that are never finished. Keycloak keeps an email address and a name for each of them, which is personal data we store without using it. The email address is also the username, so it can only be used once. We do not verify email addresses (appendix 2.1), so anyone can register with an address they do not own, and the real owner can then not create an account with it. Finally, nothing stops a script from creating many accounts. That is part of risk T4 in the risk analysis (appendix 2.3).

\subsection{What We Could Do}
We have considered four ways to handle zombie users. We have not implemented any of them.
\begin{enumerate}
  \item Keycloak could require that a new user confirms the email address before they can log in \cite{keycloak-server-admin-guide}. This stops registrations with addresses the user does not own. It does not help with the customer who just closes the app, and it needs an email server, which we do not have (appendix 2.1).
  \item A job in the API could regularly ask Keycloak for its users and delete the accounts that are older than, for example, a week and still have no customer. This removes zombie users after they have appeared. The downside is that the API would need its own client in Keycloak with the right to delete users, and a bug in the job could delete real customers.
  \item Keycloak could call code of our own when somebody registers \cite{keycloak-server-admin-guide}, so the API knows about every account from the start. That needs an extension to Keycloak written in Java, and the API would still have a customer without a name and address until onboarding is done.
  \item The API could create an empty customer the first time it sees a new user, and onboarding would then fill in the name and address. This closes the gap between Keycloak and the database, but it only moves the problem, because the database would then hold empty customers.
\end{enumerate}

\subsection{Why We Do Not Handle It}
We have chosen not to handle zombie users in this version. The supervisor agreed to postpone it at the meeting on 3 November, and it is not part of our requirements.

The main reason is that zombie users do not break anything. They cannot reach other users' data, and the app already sends a user without a customer to the onboarding screen. The most common case, a customer who stops halfway, is therefore already handled.

Every solution also needs something new. It is either an email server, a client in Keycloak that may delete users, a Keycloak extension in Java or a job that deletes accounts on its own. For a prototype with few users, that is more code and more risk than the zombie users themselves. If it is ever needed, an administrator can find and delete them by hand in Keycloak's Admin Console. We would rather spend the time on our must-have requirements, which are about subscriptions, orders and expiry dates.

If PrepMeUp were used for real, we would first turn on email verification, brute force detection and a password policy. All three are settings in the realm file, and only email verification also needs an email server (appendix 2.1). After that we would add the cleanup job, because it is the only option that also removes the accounts of customers who stop halfway.

\section{Onboarding Flow: Administrator}\label{sec:onboarding-admin}
This section shows how a new administrator gets access to the admin panel. An administrator cannot register themselves like a customer. Only an existing administrator can make someone an administrator, so the flow assumes that at least one administrator already exists. The first one is created by hand (see How a User Gets a Role).

\drawiofig[\linewidth]{onboarding-admin}{Onboarding of a new administrator, from creation in the Keycloak Admin Console to access to the admin panel.}{fig:onboarding-admin}

Figure~\ref{fig:onboarding-admin} has four lanes: the existing administrator, the new administrator, Keycloak, and the admin panel with the Web API. The flow has five parts.

\paragraph{1. Create the user in Keycloak.} The existing administrator logs in to the Keycloak Admin Console. Users are created there, because the admin panel has no page for it yet. Our admin role only gives access to the admin panel and the admin endpoints of the API. It does not give access to the Admin Console by itself, so the existing administrator also needs a Keycloak account that is allowed to manage users.

In the Admin Console the existing administrator creates a user in the prepmeup realm with email, first name and last name. Keycloak gives the user the household role automatically, as it does for every new user (see Realm Roles).

\paragraph{2. Temporary password and admin role.} The existing administrator sets a temporary password for the user. Because the password is temporary, Keycloak marks the user with a required action, Update Password. Then the existing administrator gives the user the realm role admin. From now on, every token Keycloak issues for this user has the admin role in the realm\_access claim.

\paragraph{3. Hand over the login.} The existing administrator gives the new administrator their email and temporary password. This happens outside the system, for example in person. Keycloak cannot send an invitation email, because we have not set up an email server for the realm.

\paragraph{4. First login.} The new administrator opens the admin panel and clicks Sign in. The admin panel sends them to Keycloak's login page with the Authorization Code flow and PKCE, as in Figure~\ref{fig:keycloak-login-flowchart}. They log in with the temporary password. Keycloak sees the required action and asks for a new password before it lets them continue. When the new password is saved, Keycloak removes the required action and sends the browser back to the admin panel with an authorization code. The admin panel exchanges the code for tokens and keeps them in memory only (see Where the Admin Panel Keeps the Token). The temporary password cannot be used after this.

\paragraph{5. Check the role.} The admin panel calls GET /admin/ping with the access token. The API first checks the token. Then the claims transformation turns the roles in realm\_access into role claims, and the admin policy checks that the user has the admin role. If the role is there, the API answers 200 OK, and the admin panel shows the dashboard. The new administrator is now onboarded.

If the existing administrator forgot to give the admin role, the API answers 403 Forbidden. The admin panel then shows that the account has no access and offers a sign-out button. The user is not signed out automatically, so they can see why they were turned away.

The admin panel has no onboarding screen like the customer app. An administrator has no name or address in our database, because everything the API needs to know about them is in the token.

\section{Order Lines}\label{sec:order-lines}
This section explains what an order contains and why we store it the way we do. When a customer signs up (FR-01), they choose how many packages of each package type the first order has, for example two adult packages and one child package.

\paragraph{One line per package type.} The order keeps a list of order lines. A line has a package type and a quantity, and we do not store one row for every package. A package is not tied to a person (appendix 1.2), so two adult packages are just the same package twice. It also suits FR-19, which makes the next order from the package types and quantities of the previous one. A package type that has been ordered is never edited. The order only needs to point to it, so an old order keeps its contents even when the administrator replaces the package type.

\paragraph{The rules.} The rules are in the Domain project, so we can test them without a database. A quantity must be at least one, and a package type that has been replaced cannot be ordered. An order needs at least one line, and a package type can only appear once in an order. The database checks the quantity and the one line per package type as well, because it is the last place where wrong data can be stopped.

\paragraph{From request to answer.} The app sends the lines in POST /subscription. The API checks that the list is not empty and that every quantity is at least one. The service then looks up the package types. If one of them is unknown, replaced or used twice, the service gives an error, and the API turns it into 400 Bad Request. A customer who is not onboarded gets 404, and a customer who already has a subscription gets 409. In the answer, every line has the name of its package type, so the app can show it without a second request, also for a type that has been replaced.

\paragraph{In the app.} The customer chooses the quantities on one screen, with a counter for each active package type, and confirms on the next screen. If the API answers 409, the customer already has a subscription. The app says so and offers to go to the home screen. If the API answers 400 because a package type is no longer available, the app says that and goes back to the order. For any other error the app shows a message and a button to try again.
