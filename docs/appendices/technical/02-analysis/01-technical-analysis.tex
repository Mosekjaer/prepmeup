\section{Purpose}
In this appendix we go through the technologies we use in PrepMeUp and explain why we picked them. For the bigger choices we also show the alternatives we looked at. The system is made of one backend, two user interfaces (an app for customers and a web page for administrators) and a shared client package that both user interfaces use to talk to the backend. The requirements are in appendix 1.2.

\section{Technology Stack}
This section is a short overview of our technology stack. The reasons behind the choices come in the sections after it.

\subsection{Clients}
The client code is written in TypeScript.
\begin{itemize}
    \item Customer app: Expo (React Native) with Expo Router \cite{expo-router-introduction}. Android is the main target (NFR-06), but Expo can also run the app in a browser, which is handy while developing.
    \item Admin panel: React with Vite and React Router. Runs in the browser.
    \item API client (packages/api-client): generated from the API's OpenAPI document with NSwag \cite{nswag-typescript-client-generator}. Nobody edits it by hand.
    \item All three are in one npm workspace, so npm install, npm test and npm run typecheck only have to be run once in clients/.
\end{itemize}

\subsection{Backend}
\begin{itemize}
    \item ASP.NET Core Web API on .NET 10 with controllers and dependency injection \cite[sec.~1.2.1]{desanctis-web-apis-aspnet-core}.
    \item Serilog for logging and ProblemDetails for error responses \cite[secs.~6.2.4 and 7.4.1]{desanctis-web-apis-aspnet-core}.
    \item An OpenAPI document with Swagger UI. We use the document as the contract between the API and the clients \cite[sec.~3.2.1]{desanctis-web-apis-aspnet-core}.
    \item CORS that only allows the admin panel and the customer app \cite[sec.~3.1.1]{desanctis-web-apis-aspnet-core}.
    \item A health check endpoint.
    \item A background service that will check expiry dates and plan the next order (FR-04, FR-19).
    \item Configuration and secrets come from environment variables.
\end{itemize}

\subsection{Data}
We use SQL Server 2022 in Docker and access it through EF Core \cite[sec.~4.2.2]{desanctis-web-apis-aspnet-core}. The schema is created with EF Core Migrations (code first). The database port is not open to the host, so only the API container can reach it, and the data is kept in a Docker volume so it is not lost when the containers are recreated.

\subsection{Authentication}
Login is handled by Keycloak 26, which runs in the same docker compose as the API. We have one realm, prepmeup, with two roles: household for customers and admin for administrators. The role is still called household from before the requirements were changed, but it means a customer (appendix 1.2). Customers can sign up themselves and get the household role automatically \cite[secs.~Enabling user registration and Using default roles]{keycloak-server-admin-guide}. The realm is saved in infra/keycloak/realm-prepmeup.json, so everyone in the group gets the same setup when they start Keycloak.

\subsection{Test}
The backend has unit tests (NUnit and NSubstitute) against the Domain and Application layers and integration tests that start the whole API. The clients are tested with Vitest. GitHub Actions runs all of it on every pull request, and a pull request cannot be merged unless it is green.

\subsection{Tools}
Locally, one docker compose command starts the API, the database and Keycloak. It works the same on Windows and Linux. In production we deploy with Coolify on a server one of us owns (section~\ref{sec:deployment}). We use GitHub for the code and CI and a self-hosted Kaneo as task board.

\section{Backend Architecture}
\label{sec:backend}
The backend is one ASP.NET Core Web API. It serves both user interfaces and will also run the scheduler. Here we describe how the code inside it is split up.

\subsection{Four Layers}
A layered architecture splits the code into layers stacked on top of each other, where a layer may only use the layers below it. The idea is to keep things apart, so a layer can be changed or tested on its own \cite[ch.~3]{microsoft-application-architecture-guide}. We have four layers, and each one is a separate project in the solution:
\begin{center}
\begin{tabular}{@{}p{3.6cm} p{5.3cm} p{5.3cm}@{}}
\textbf{Project} & \textbf{Does} & \textbf{Does not} \\
\hline
Api & Routing, input validation, mapping between contracts and domain, status codes, authorization & Business rules. Talking to the database directly \\
\hline
Application & Runs the use cases and defines the repository interfaces and transactions & Knowing about HTTP, controllers, EF Core or SQL \\
\hline
Domain & Entities and rules: customer details, subscription, orders, package types, expiry & Referencing any other project \\
\hline
Infrastructure & EF Core configuration, queries, migrations & Making decisions. It only reads and writes \\
\hline
\end{tabular}
\end{center}
The scheduler will be placed in the Api project because it runs in the same process. It will call the same use cases as the controllers, so an order is planned by the same rules no matter if a user or the scheduler starts it. Things like authentication, logging and error handling are set up once in Program.cs and are not part of any one layer.

\subsection{Which Way the Dependencies Point}
In the usual layered design, the data access layer is at the bottom, so the business logic depends on it \cite[ch.~5]{microsoft-application-architecture-guide}. We turned that last dependency around. Api uses Application, and Application uses Domain. Application defines the interfaces it needs, for example a repository for customers, and Infrastructure implements them with EF Core. Api only knows about Infrastructure at startup, where the implementations are registered in dependency injection.

This is the Dependency Inversion Principle: the part with the business rules should not depend on the part with the technical details, and both should depend on an interface \cite[ch.~4, pp.~139--141]{freeman-head-first-design-patterns}. For us, the rule is when a customer needs the next order, and the detail is that the orders are stored in SQL Server. Goldman calls this structure Clean Architecture \cite[sec.~8.4.1]{goldman-maui-in-action}.

\subsection{Why Domain Has No References}
The Domain project has no project references and no NuGet packages. That means the most important rules in the product (what a customer must fill in, what goes in a package type, when an order expires and when the next one is planned) are plain C\# classes. We can test them by creating a customer in a unit test and checking the result, without a database or anything to fake. Goldman describes this as a strict rule in Clean Architecture \cite[sec.~8.4.2, p.~262]{goldman-maui-in-action}.

A nice side effect is that the compiler checks it for us. Domain does not reference EF Core, so if someone tries to use EF Core in Domain, the build fails. This is also why we map entities to tables with EF Core's Fluent API in Infrastructure instead of attributes on the entities \cite[sec.~4.3.3]{desanctis-web-apis-aspnet-core}.

The test projects follow the same structure. The unit tests use Application and Domain and replace the repositories with NSubstitute fakes, and the integration tests start the whole API (section~\ref{sec:data}).

\subsection{Alternatives}
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
One Web API project & Least code. Controllers talk to the database directly. & Business rules end up in the controllers, cannot be tested without a database, and the scheduler would need its own copy. \\
\hline
Normal layers (Api, business, data) & The structure most of us know. & The business layer depends on EF Core, so testing it still needs a database or a fake EF Core. \\
\hline
Layers with the data dependency turned around & Domain has no technical details and can be tested without a database. The compiler checks the layers. & Four projects and extra interfaces for a small system. Every new table means an entity, a configuration, a repository and an interface. \\
\hline
\end{tabular}
\end{center}
We went with the last option. It does give more files, but they are the same kinds of files every time, and we always create them in the same order, starting with Domain. The rules for expiry and the next order are where we are most likely to make mistakes, so we wanted to be able to test those on their own.

\section{Choice of Client Technologies}
\label{sec:clients}
We have two kinds of users. Customers use an app on their phone, and administrators use a web page on a computer to send out orders. According to the requirements, the customer app must run on Android in version 1.0, and the admin interface must be a web application (appendix 1.2).

\subsection{Customer App}
At the meeting on 15-09 we decided to build the customer app with Expo. The course teaches .NET MAUI for native apps and React for the web, so we compared those two with Expo, which is built on React Native.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
.NET MAUI & Taught in the course. Same language as the backend (C\#). Builds apps for Android, iOS and Windows \cite[sec.~1.2]{goldman-maui-in-action}. & The admin panel would still be React, so we would have two UI frameworks, two languages and two test tools. \\
\hline
Only a React web app & Taught in the course. One framework for both user interfaces. & Not an Android app, which the requirements ask for. \\
\hline
Expo (React Native) & Same React, hooks and TypeScript as the admin panel. Builds an Android app and can also run on the web. File-based navigation with Expo Router. & Not in the course. React Native uses native views instead of HTML, so not everything we know about the DOM and CSS applies. \\
\hline
\end{tabular}
\end{center}

We chose Expo. React does not care where it renders: React DOM renders to the browser and React Native renders to the phone \cite[sec.~1.5.1, pp.~16--17]{mardan-react-quickly}. So components, state and hooks work the same way in both of our apps, and everyone in the group can work on both. With MAUI we would have split the group into a C\# half and a React half.

In Expo Router each file in the app folder is a screen \cite{expo-router-introduction}. It works like React Router, except the routes come from the files.

\subsection{Admin Panel}
The admin panel is a normal React app built with Vite, and it uses React Router for navigation \cite[ch.~13]{mardan-react-quickly}.
The admin panel is not deployed yet (appendix 10.3). One thing we need to remember when we deploy it: the web server has to return the same page for every URL, otherwise a user who opens a sub page directly gets a 404 \cite[sec.~13.2.3]{mardan-react-quickly}.

\subsection{Why Two Apps}
Since Expo can also build for the web, one app could in theory be used by both customers and administrators. We decided not to do that. The two users need different screens and have different roles, so a shared app would need role checks on every screen, and the admin screens would end up inside the customer app. The admin panel only has to run in a browser, and for that a plain React app with Vite is simpler than React Native running on the web. Having two apps also means each has its own Keycloak client (section~\ref{sec:auth}).

The downside is two apps to maintain. To keep that manageable they share everything that is not UI: the API client, the TypeScript setup and the npm workspace.

\subsection{The Generated API Client}
Both apps call the API through packages/api-client, which NSwag generates from the API's OpenAPI document. Goldman uses NSwag in the same way for a .NET client and points out that it pays off more as the API grows \cite[sec.~8.3, p.~255]{goldman-maui-in-action}.

For us the main benefit is that the apps do not have to build URLs, handle JSON or write their own types for the data. A screen just calls a method on the client and gets typed objects back. When the API changes we regenerate the client, and if an app still uses something that was removed, the type check in CI fails instead of the app crashing later. The login token is added in one place: each app gives the client a function that returns its token, so the generated code does not need to know anything about Keycloak. The apps get the token with a library each. The customer app uses Expo's AuthSession \cite{expo-auth-session}, and the admin panel uses oidc-client-ts \cite{authts-oidc-client-ts} through react-oidc-context \cite{authts-react-oidc-context}. Both do the Authorization Code flow with PKCE (section~\ref{sec:auth}), so we do not write that part ourselves. Business rules stay in the backend, and the apps only show what the API returns.

\subsection{Testing the Clients}
Both apps are tested with Vitest, which runs the tests in jsdom instead of a real browser \cite{vitest-test-environment}, and React Testing Library \cite{testing-library-react-intro}. The tests are in a tests/ folder in each app and run in CI.

In the admin panel we render components and check what the user sees, for example that the dashboard shows its heading. The customer app is harder, because React Native cannot run in Vitest. We work around it by using React Native for Web in the tests, so the components render as HTML. This means we test logic and state, but not how the screen actually looks on a phone.

The tests never call the real API. We replace the API client with a fake that returns fixed data, so we can test both the list of items and the error message. Navigation is tested the same way with a fake router. What we cannot test like this is how the app looks on Android and the login with Keycloak. We check those by hand on a phone and in the acceptance test (appendix 6.1).

\section{Choice of Authentication}
\label{sec:auth}
Both customers and administrators need to log in. At the meeting on 15-09 we agreed to use an external login provider, and the options we came up with were Firebase, Keycloak, Clerk and OAuth. We also looked at what the course shows, which is ASP.NET Core Identity with our own JWTs.

OAuth turned out not to be an option on its own. OAuth 2.0 is a standard for how an app gets a token, and OpenID Connect adds login on top of it \cite[sec.~8.1.2]{goldman-maui-in-action}. Keycloak implements both, so the actual choice was between the services.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
ASP.NET Core Identity with own JWT & Taught in the course \cite[sec.~9.2]{desanctis-web-apis-aspnet-core}. Everything stays in our own API. & We would have to write login, token refresh, password reset and email verification ourselves. Not an external provider. \\
\hline
Firebase Authentication & Hosted by Google, quick to start with, good mobile SDKs. & User data is stored at Google. Roles need extra setup. Made for the rest of Firebase, which we do not use. \\
\hline
Clerk & Hosted, with ready-made login screens for React and Expo. & User data is stored at a third party. Costs money above the free tier. Hard to move away from. \\
\hline
Keycloak & Open source and free. Runs in our own compose. Uses standard OpenID Connect, so the API only needs normal JWT validation. Has roles built in. & Heavier to run (Java) and more to set up. We have to run and update it ourselves. Only mentioned briefly in the course. \\
\hline
\end{tabular}
\end{center}

We chose Keycloak, mostly because we already host everything else ourselves. Kaneo, the API and the database all run on our own server, so Keycloak is just one more container. It also means that customers' names, addresses and orders do not end up at Google or another company, which makes GDPR simpler.

Another reason is that the apps log in with a standard flow (Authorization Code with PKCE, which is what is recommended for mobile and browser apps \cite[sec.~2.1.1]{ietf-rfc9700-oauth-security-bcp}), and the API only checks a normal JWT. If we ever switch provider, the API code does not change much. Logging in by sending the password directly through the app is turned off \cite[sec.~2.4]{ietf-rfc9700-oauth-security-bcp}. Finally, the household and admin roles are put into the token \cite[sec.~Role scope mappings]{keycloak-server-admin-guide}, so the API can use them. Keycloak stores them in a different claim than ASP.NET Core expects, so the API maps them to normal roles before it checks them.

The price is that Keycloak takes more work to set up and uses more memory than the API itself. We think that is fine, because the realm file makes the setup the same for everyone, and learning to use a real login provider is something we want to get out of the project.

\section{Keycloak Features}
\label{sec:keycloak-features}
Keycloak can do a lot more than we need. At the meeting on 6/10 the supervisor asked us to write down which features we use, which we have chosen not to use, and why. The setup is in the realm file, which Keycloak reads when it starts the first time \cite{keycloak-import-export}. Anything that is not in the file has Keycloak's default value. This section will be updated as we start using more of Keycloak.

\subsection{Features We Use}
\begin{center}
\begin{tabular}{@{}p{4cm} p{10.4cm}@{}}
\textbf{Feature} & \textbf{Why} \\
\hline
Realm file with environment variables & The whole setup is in the repository, so everyone gets the same realm. Addresses that differ between local and production are filled in from environment variables \cite[sec.~Using Environment Variables within the Realm Configuration Files]{keycloak-import-export}. \\
\hline
Authorization Code flow with PKCE (S256) & The recommended flow for apps that cannot keep a secret \cite[sec.~2.1.1]{ietf-rfc9700-oauth-security-bcp}. Keycloak is set to require S256, so a login without PKCE is refused \cite[sec.~Capability Config]{keycloak-server-admin-guide}. \\
\hline
Two public clients & One for the customer app and one for the admin panel, each with its own redirect addresses. Neither can keep a client secret, because the code runs on the user's phone or in the browser. \\
\hline
Self-registration with email as username & A new customer must be able to create an account without an administrator (FR-01). Keycloak adds a register link to its login page \cite[sec.~Allowing users to self-register]{keycloak-server-admin-guide}. \\
\hline
Realm roles and a default role & Household and admin are realm roles, see appendix 4.1. Every new user gets the household role automatically \cite[sec.~Using default roles]{keycloak-server-admin-guide}. \\
\hline
Audience mapper & Puts our API's name in the token's audience claim \cite[sec.~Hardcoded audience]{keycloak-server-admin-guide}, so the API can refuse tokens that were made for something else \cite[sec.~2.3]{ietf-rfc9700-oauth-security-bcp}. \\
\hline
Token lifetimes & Access tokens live 15 minutes. The login session ends after 30 minutes without use and after 10 hours at most \cite[sec.~Session and token timeouts]{keycloak-server-admin-guide}. \\
\hline
Logout through Keycloak & The app ends the session at Keycloak and is sent back to an address that is allowed in the realm \cite[sec.~RP-Initiated Logout]{keycloak-server-admin-guide}. \\
\hline
\end{tabular}
\end{center}

\subsection{Features We Have Chosen Not to Use}
\begin{center}
\begin{tabular}{@{}p{4cm} p{10.4cm}@{}}
\textbf{Feature} & \textbf{Why not} \\
\hline
Password grant (Direct Access Grants) & The app would get the user's password. It must not be used \cite[sec.~2.4]{ietf-rfc9700-oauth-security-bcp}, and it is turned off on both clients. \\
\hline
Implicit flow & Sends the token in the URL. It should not be used \cite[sec.~2.1.2]{ietf-rfc9700-oauth-security-bcp}, and it is turned off. \\
\hline
Token introspection & The API would ask Keycloak about every token. Keycloak only allows this for confidential clients \cite[sec.~Introspection endpoint]{keycloak-securing-apps-oidc}, and it costs a network call per request. We check the token locally instead, see section~\ref{sec:block-token}. \\
\hline
Client roles & We only have two roles that mean the same in both apps, so realm roles are enough (appendix 4.1). \\
\hline
Login with Google and other providers & Keycloak can let users log in through another provider \cite[sec.~Social Identity Providers]{keycloak-server-admin-guide}. We chose Keycloak to keep user data out of Google and similar companies (section~\ref{sec:auth}), so this would go against that. \\
\hline
User federation (LDAP) & Used when users already exist in another directory \cite[sec.~Lightweight Directory Access Protocol (LDAP) and Active Directory]{keycloak-server-admin-guide}. All our users are new. \\
\hline
Two-factor login (OTP) & Not needed for customers. It may make sense for administrators later \cite[sec.~One Time Password (OTP) policies]{keycloak-server-admin-guide}. \\
\hline
\end{tabular}
\end{center}

\subsection{Not Set Up Yet}
Some features are off only because the realm file does not mention them. We have not decided against them, and most of them should be turned on before the system is used for real.

Brute force detection is off by default \cite[sec.~Brute force attacks]{keycloak-server-admin-guide}. Since Keycloak is on a public server, it should be on. There is also no password policy, so any password is accepted \cite[sec.~Password policies]{keycloak-server-admin-guide}.

Email verification and password reset need an SMTP server \cite[sec.~Configuring email for a realm]{keycloak-server-admin-guide}. Password reset is turned on in the realm, but we have no SMTP server yet, so the email cannot be sent. Without email verification anyone can register with an address they do not own, which is part of the zombie user problem (PMU-80).

Refresh tokens can be reused until they expire. For public clients they should be rotated \cite[sec.~2.2.2]{ietf-rfc9700-oauth-security-bcp}, which Keycloak calls Revoke Refresh Token \cite[sec.~Session and token timeouts]{keycloak-server-admin-guide}. The admin panel already renews its access token with a refresh token, so this should be turned on now. The customer app does not use refresh tokens yet.

Finally, Keycloak only logs errors by default and does not save login events \cite[sec.~Auditing user events]{keycloak-server-admin-guide}.

\subsection{Blocking a Token Before It Expires}
\label{sec:block-token}
There are good reasons to want to block a token: it may have been stolen, the user may have been removed as admin, or the account may have been closed. The problem is that the API checks the token on its own. It has Keycloak's public key and only looks at the signature and the claims, so Keycloak cannot take a token back once it is issued. The token works until its expiry time \cite[sec.~4.1.4]{ietf-rfc7519-jwt}. Even if all of a user's sessions are signed out in Keycloak, access tokens already issued are still valid until they expire \cite[sec.~Signing out all active sessions]{keycloak-server-admin-guide}.

We looked at three ways to block tokens. The first is introspection \cite{ietf-rfc7662-token-introspection}, where the API asks Keycloak on every request whether the token is still active. It works, but every request depends on Keycloak, and the API would need its own confidential client.

The second is revocation \cite{ietf-rfc7009-token-revocation}. A client can tell Keycloak to revoke a token \cite[sec.~Token Revocation endpoint]{keycloak-securing-apps-oidc}. For a token the API checks itself, that only helps if the API also asks Keycloak, so it comes back to introspection \cite[sec.~3]{ietf-rfc7009-token-revocation}.

The third is Keycloak's not-before policy. Keycloak can mark all tokens issued before a certain time as invalid and push this to the apps. The push only reaches apps that use Keycloak's own adapter \cite[sec.~Revoking active sessions]{keycloak-server-admin-guide}. Our API uses Microsoft's JWT validation, so it would not know.

We chose short tokens instead, which is the alternative RFC 7009 mentions \cite[sec.~3]{ietf-rfc7009-token-revocation}. A stolen token works for at most 15 minutes, and a user who loses the admin role keeps it in the API for at most 15 minutes. We accept that for PrepMeUp, because a customer's data is not critical enough to justify a call to Keycloak on every request.

\subsection{IP Checks}
Keycloak 26.3 has no built-in way to allow or refuse a login based on the user's IP address. The conditions that can be used in a login flow look at the user, its roles and attributes, the client scope and the user's credentials, not the network \cite[sec.~Available conditions]{keycloak-server-admin-guide}. Brute force detection locks the user's account, not an IP address. Keycloak's own advice is to log failed logins with the IP address and let other software block the address in the firewall \cite[sec.~Downside of Keycloak brute force detection]{keycloak-server-admin-guide}.

We do not check IP addresses. Our customers use the app on their phones, and a phone changes IP address all the time, so a list of allowed addresses would not work for them. If we want to block addresses that try many passwords, it should be done in front of Keycloak, in Coolify's proxy or the server's firewall, and not in Keycloak itself.

\section{Choice of Deployment}
\label{sec:deployment}
At the same meeting we agreed that we need one shared deployment. Once there is an administrator sending out orders, everyone has to use the same data, and that does not work if each of us only runs the system on our own computer.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
Only local & Nothing to set up. & No shared data, no real administrator, and no testing on a phone outside the home network. \\
\hline
Azure & Used in the course. Managed services. & Costs money or student credits that run out. Many services to set up. \\
\hline
Coolify on own server & Free, because the server already exists. Deploys directly from docker compose and handles HTTPS certificates \cite{coolify-traefik-overview}. & Depends on one server and one group member. Not in the course. \\
\hline
\end{tabular}
\end{center}

We chose Coolify. The production setup has its own compose file, which is a bit different from the local one. No ports are opened, because Coolify's proxy handles HTTPS and forwards traffic to the containers. Keycloak runs in production mode with its own PostgreSQL database, so user accounts are kept separate from the application data. All URLs and passwords come from environment variables in Coolify, and the stack does not start if one of them is missing.

\section{Choice of Data Access and Database}
\label{sec:data}

\subsection{EF Core}
We looked at two ways to use a SQL database from .NET: EF Core, which is a full ORM \cite[sec.~4.3]{desanctis-web-apis-aspnet-core}, and Dapper, where you write the SQL yourself and Dapper turns the result into objects \cite{dapperlib-dapper}.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
EF Core & Queries are written in LINQ. Tracks changes, so everything can be saved in one transaction. Creates the schema and migrations from the C\# classes. & More to learn. The generated SQL can be slow for complex queries and bulk inserts. \\
\hline
Dapper & Full control over the SQL. Very fast. & No change tracking and no schema generation. All SQL and all schema changes are written by hand and kept in sync with the classes by hand. \\
\hline
\end{tabular}
\end{center}

We chose EF Core. Dapper makes sense when you need full control over the SQL or performance really matters. Performance is its main feature \cite{dapperlib-dapper}, while an ORM hides the SQL and adds some overhead \cite[sec.~4.3.1]{desanctis-web-apis-aspnet-core}. That is not our situation. We have a small amount of data, and the heaviest query (finding items close to expiry) runs in the background, so no user is waiting for it. Change tracking is actually useful for us, because the next order is created as a copy of the previous one with all its packages, and the order and its packages have to be saved together \cite[sec.~4.3.4]{desanctis-web-apis-aspnet-core}. With EF Core the C\# classes are also the only description of the database, where Dapper would give us classes, SQL and migration scripts to keep in sync.

If a query gets slow later, EF Core lets us write that one query in raw SQL \cite{microsoft-efcore-sql-queries}. Since the data access is behind the repository interfaces, such a change stays inside Infrastructure.

\subsection{Migrations}
If a database is changed by hand, or the scripts are not in version control, the databases on different machines slowly drift apart and things break when the app runs. A change one of us makes to the schema has to be something the others can run on their own database \cite{dbup-philosophy}. So we knew we wanted migrations. The question was which kind.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
EF Core Migrations, code first & Generated from the classes, so classes and schema match. Can be rolled back and reviewed in the pull request. & The generated SQL has to be checked. For example, a rename can be generated as drop and add, which deletes the data. \\
\hline
DbUp with SQL scripts & Plain SQL that is easy to read. & Classes and schema updated by hand. \\
\hline
Database first & Good if a database already exists. & There is no existing database, and we want the domain to decide the schema. \\
\hline
Only create the schema at startup & No migration files. & Only works on an empty database, so the schema cannot be changed later. \\
\hline
\end{tabular}
\end{center}
The table is based on \cite[secs.~4.3.2 and 4.3.5]{desanctis-web-apis-aspnet-core}, \cite{microsoft-efcore-managing-migrations}, \cite{microsoft-efcore-create-drop-apis} and \cite{dbup-docs}.

We chose EF Core Migrations with code first. The schema is only changed through a new migration, never by hand, and the migration is committed in the same pull request as the change to the classes, so the reviewer can see the SQL. Right now the API runs the missing migrations itself when it starts, both locally and in production. That is simple, but if a migration fails, the API does not start, and if we ever run more than one API container, they could try to migrate at the same time. De Sanctis recommends a migration bundle instead, which runs as its own step before the new API starts \cite[sec.~12.4.4, p.~421]{desanctis-web-apis-aspnet-core}. Appendix 10.3 describes the bundle, but it is not in the compose file yet (see open decisions).

\subsection{SQL Server}
Our data has a lot of relations: a customer has a subscription and orders, an order has packages of a package type, and a package type contains items. It is also important that an order and its packages are saved together. Transactions and foreign keys are exactly what relational databases are good at \cite[secs.~4.1 and 4.1.1]{desanctis-web-apis-aspnet-core}.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
SQL Server & Used in the course, so the slides and exercises apply directly. Works well with EF Core. Runs in Docker. & Big image. The free versions have limits. \\
\hline
PostgreSQL & Free and light. Works well with EF Core. We already use it for Keycloak. & Not used in the course. Nothing in our requirements needs it. \\
\hline
MongoDB & Flexible schema. Can scale to several servers. & No foreign keys, so the app has to keep track of the relations \cite{mongodb-data-consistency}. We have many relations and one server. \\
\hline
\end{tabular}
\end{center}

We chose SQL Server, mainly because it is what the course uses, and PostgreSQL did not give us anything we needed. Because of the layers, the choice only shows up in Infrastructure, so switching later would mean a new EF Core provider and new migrations, but no changes to the rules or the API \cite[secs.~4.1.2 and 4.3.1]{desanctis-web-apis-aspnet-core}.

\subsection{Database in Tests}
The unit tests do not use a database, since they test Domain directly and Application with fake repositories. The integration tests start the whole API, but without a database. They replace the repository with a fake that keeps the data in a list, so they test routing, authentication, roles, status codes and the services. This means that our EF Core mapping, our queries and our migrations are not tested automatically. The migrations are only run against SQL Server when the API starts locally and when we deploy.

Microsoft's guide describes the options for testing against a database: the real database system, an in-memory SQLite database or fake repositories \cite{microsoft-efcore-testing-strategy}. When the system gets more tables (PMU-91), we need tests of the repositories. The guide recommends testing against the same database system as production, because SQLite does not behave exactly like SQL Server, and our migrations are made for SQL Server.

\section{Version Control and Git Workflow}
\label{sec:git}
The code is on GitHub. The course uses GitLab CI, but the ideas are the same, so we use GitHub Actions. Coolify also gets the production compose file and the images from GitHub.

We looked at three workflows: trunk-based development \cite{hammant-trunk-based-development}, GitHub Flow \cite{chacon-github-flow-2011} and Git Flow \cite{driessen-git-branching-model}. We chose GitHub Flow. Driessen, who came up with Git Flow, recommends a simpler workflow like GitHub Flow for teams that deliver a web application continuously and only have one version running \cite{driessen-git-branching-model}. That is us. Git Flow is made for software with planned versions and several versions in use at once, so its extra branches would not help us. Pure trunk-based, where everyone commits directly to the main branch, would mean no code review before merge, and we want that.

In practice:
\begin{itemize}
    \item The main branch is the only long-lived branch and should always be deployable.
    \item We work on short branches that start with the type of change and the number of the Kaneo task, for example feat/pmu-74-customer-onboarding.
    \item Commit messages follow Conventional Commits, for example feat(api): add customer endpoint.
    \item Everything goes into the main branch through a pull request with green CI and one review. We squash merge, so each pull request becomes one commit.
    \item At the end of a sprint we tag a release on the main branch, for example v0.1.0.
\end{itemize}
Branch names and commit messages are checked by git hooks locally and again in GitHub Actions. See appendix 10.1.

\section{Operations, CI and Security}
\label{sec:ops}
Here we explain the choices we made about running the system and keeping it secure, and what we know is still missing. The exact deployment steps and how to roll back are in appendix 10.3.

\subsection{Containers}
Every service runs in a Docker container, both locally and in production. The API image is built in two steps with a multi-stage build \cite{docker-multi-stage-builds}\cite{microsoft-aspnetcore-docker}: first the code is built with the .NET SDK, and then only the finished files are copied into a smaller runtime image. That way the SDK and the source code are not in the image we run. The API also runs as a normal user instead of root, so a bug in the API does not give an attacker root in the container.

Our Keycloak image is the official one with our realm file copied in. One thing we learned is that Keycloak only imports the realm the first time \cite[sec.~Importing a realm during startup]{keycloak-import-export}. After that, changes to the file do not reach the running Keycloak, so they also have to be made in the admin console.

In production SQL Server uses a fixed image version (a specific cumulative update) instead of latest, so a new version cannot sneak into production without a commit. Our own images for the API and Keycloak are tagged with the commit they were built from, but the production compose file falls back to the main tag if no tag is set, and the PostgreSQL image for Keycloak only fixes the major version (see open decisions).

\subsection{CI and Deployment}
The CI workflow first builds and tests the backend and the apps. If everything is green on the main branch, it builds the images, pushes them to GitHub Container Registry and tells Coolify to deploy them. A second workflow checks branch names and pull request titles.

Continuous integration means integrating often and checking every integration with an automated build that runs the tests \cite{fowler-continuous-integration}. We have also made the pipeline the only way into production. If a test fails, no image is built and nothing is deployed, and automatic deployment is turned off in Coolify, so there is no way around it. Production also runs the exact image that was tested, because Coolify does not build anything itself.

We had a bug in the deploy job at first. It only failed if Coolify answered with an error, so when Cloudflare answered with a redirect, the job was green even though nothing was deployed. Now the job only passes if Coolify answers 200. More about this in appendix 10.3.

\subsection{Network and HTTPS}
Only Coolify's proxy can be reached from the internet. It handles HTTPS and forwards the requests to the API and Keycloak inside the Docker network. In this setup only the proxy needs a certificate \cite{microsoft-kestrel-reverse-proxy}. No container opens a port in production, so the databases can only be reached from inside the network (see appendix 3.1). The traffic inside the network, for example between the API and SQL Server, is not encrypted. We accept that because it never leaves the server.

\subsection{Login in the API}
The API checks every token it gets: it must be signed by Keycloak, come from the right issuer, be meant for our API and not be expired \cite[sec.~9.2.5]{desanctis-web-apis-aspnet-core}\cite[secs.~4.1.1, 4.1.3, 4.1.4 and 7.2]{ietf-rfc7519-jwt}. Tokens are valid for 15 minutes, since the advice is to keep them short \cite[sec.~9.1.2]{desanctis-web-apis-aspnet-core}.

In production the API talks to Keycloak over the internal network, but the tokens contain Keycloak's public address. Because the two addresses are different, we had to set the expected issuer by hand. Chapter 8 in the report describes how we found this. For the same reason the API is allowed to fetch Keycloak's settings over plain HTTP inside the network. Microsoft recommends only doing that in development \cite{microsoft-jwtbearer-requirehttpsmetadata}, so it only works because the traffic stays internal.

The requirements NFR-09 to NFR-11 say what the API must refuse. A request without a token gets 401 (NFR-11). Customers must get 403 on admin endpoints (NFR-10), so the admin endpoints require the admin role through an authorization policy, and the integration tests check both a customer token and an admin token. A customer must only see and change their own data (NFR-09). A role cannot solve this. Today the endpoints for a customer's own details have no customer id in the URL at all: the controller takes the user id from the token and passes it to the service, so there is no other customer to ask for. When orders get their own endpoints (PMU-91), a request for an order by id must also check that the order belongs to the customer in the token, and answer 403 if it does not. That check belongs in the Application layer, so it cannot be forgotten in a single controller.

CORS only allows our two apps. That is not real protection, though, because CORS is only enforced by browsers \cite[sec.~3.1.1]{desanctis-web-apis-aspnet-core}. The API still has to check authorization itself.

\subsection{Secrets}
Passwords and other secrets are only set as environment variables in Coolify, not in the repository or the images \cite[sec.~12.1.4]{desanctis-web-apis-aspnet-core}\cite{microsoft-aspnetcore-app-secrets}. That is why our images on GitHub can be public. If a secret is missing, the stack refuses to start instead of starting with an empty password. GitHub only stores the Coolify webhook and a token that can start a deployment and nothing else, and images are pushed with the temporary token GitHub Actions creates for each run.

\subsection{Known Weaknesses}
These are things we know are not good enough yet. They are also listed under open decisions.
\begin{itemize}
    \item The API logs in to SQL Server as sa. It should have its own user that can only read and write data.
    \item If the Keycloak address is missing from the configuration, the API starts without authentication. If the connection string is missing, the API skips the migrations and only fails at the first request that needs the database. That cannot happen in production because the compose file requires both, but the API should refuse to start (NFR-07).
    \item If the database is down while the API is running, the request fails with a general error. NFR-04 asks for HTTP 503 with an English message.
    \item Both compose files run SQL Server as the Developer edition, which is free but only allowed for development and test. The Express edition is also free and is allowed in production \cite[sec.~4.2.2, p.~101]{desanctis-web-apis-aspnet-core}. Its limits, for example 10 GB per database \cite{microsoft-sql-server-2022-editions}, are far more than we need.
    \item The customer app only keeps the token in memory, so the customer has to log in again every time the app is restarted.
    \item An API should only accept HTTPS. A redirect from HTTP is not enough for an API, because the token may already have been sent in clear text \cite[sec.~HSTS and API projects]{microsoft-aspnetcore-enforce-https}. We have not checked yet how Coolify's proxy handles this.
    \item The GitHub Actions we use are pinned to a version like v4, not to a specific commit. If one of them is hacked, our pipeline would run the new code \cite[sec.~Using third-party actions]{github-secure-use}.
\end{itemize}

\section{Key Technical Decisions}
\begin{itemize}
    \item One backend serves both user interfaces, and the OpenAPI document is the contract.
    \item Business rules are only in Domain. The apps call the API through the generated client.
    \item EF Core instead of hand-written SQL.
    \item The database cannot be reached from outside Docker.
    \item No MediatR. It solves a problem we do not have and is not part of the course.
    \item We build one feature at a time through all four layers, starting with Domain.
    \item All text the user sees is in English, and there is no translation (NFR-01).
\end{itemize}

\section{Open Decisions}
\begin{itemize}
    \item How the customer app stores the token between restarts, for example with Expo SecureStore, and whether it needs a library for fetching data, for example TanStack Query.
    \item Whether the customer app should also be released as a web app.
    \item A separate database user for the API instead of sa.
    \item Make the API refuse to start without a Keycloak address or a connection string outside development (NFR-07).
    \item Check that Coolify's proxy does not serve the API over plain HTTP, and that Keycloak redirects to HTTPS.
    \item Where and how the admin panel is deployed, and that it redirects to HTTPS.
    \item Whether to pin GitHub Actions to specific commits.
    \item Use SQL Server Express in production instead of Developer (section~\ref{sec:ops}).
    \item Make the image tag required in Coolify, so production cannot fall back to the newest image, and fix the PostgreSQL image to a minor version.
    \item Run the migrations as a migration bundle before the API starts, as described in appendix 10.3, or keep running them at startup and change appendix 10.3.
    \item How a customer is notified when the next order is created (FR-20), for example push notifications through Expo, e-mail or only a message in the app.
    \item Integration tests of the repositories against SQL Server when more tables are added (PMU-91).
    \item Turn on brute force detection, a password policy, refresh token rotation and email in Keycloak (section~\ref{sec:keycloak-features}).
\end{itemize}
