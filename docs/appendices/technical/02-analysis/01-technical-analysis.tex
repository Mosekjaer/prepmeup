\section{Purpose}
In this appendix we go through the technologies we use in PrepMeUp and explain why we picked them. For the bigger choices we also show the alternatives we looked at. The system is made of one backend, two user interfaces (an app for customers and a web page for administrators) and a shared client package that both user interfaces use to talk to the backend. The requirements are in appendix 1.2.

\section{Technology Stack}
This section is a short overview of our technology stack. The reasons behind the choices come in the sections after it.

\subsection{Clients}
The client code is written in TypeScript.
\begin{itemize}
    \item Customer app: Expo (React Native) with Expo Router \cite{expo-router-introduction}. Android is the main target (NFR-06), but Expo can also run the app in a browser, which is handy while developing.
    \item Admin panel: React with Vite and React Router. Runs in the browser.
    \item API client (packages/api-client): generated from the API's OpenAPI document with NSwag \cite{nswag-typescript-client-generator}. Nobody edits it by hand.
    \item All three are in one npm workspace, so npm install, npm test and npm run typecheck only have to be run once in clients/.
\end{itemize}

\subsection{Backend}
\begin{itemize}
    \item ASP.NET Core Web API on .NET 10 with controllers and dependency injection \cite[sec.~1.2.1]{desanctis-web-apis-aspnet-core}.
    \item Serilog for logging and ProblemDetails for error responses \cite[secs.~6.2.4 and 7.4.1]{desanctis-web-apis-aspnet-core}.
    \item An OpenAPI document with Swagger UI. We use the document as the contract between the API and the clients \cite[sec.~3.2.1]{desanctis-web-apis-aspnet-core}.
    \item CORS that only allows the admin panel and the customer app \cite[sec.~3.1.1]{desanctis-web-apis-aspnet-core}.
    \item A health check endpoint.
    \item A background service that will check expiry dates and plan new deliveries.
    \item Configuration and secrets come from environment variables.
\end{itemize}

\subsection{Data}
We use SQL Server 2022 in Docker and access it through EF Core \cite[sec.~4.2.2]{desanctis-web-apis-aspnet-core}. The schema is created with EF Core Migrations (code first). The database port is not open to the host, so only the API container can reach it, and the data is kept in a Docker volume so it is not lost when the containers are recreated.

\subsection{Authentication}
Login is handled by Keycloak 26, which runs in the same docker compose as the API. We have one realm, prepmeup, with two roles: household for customers and admin for administrators. Customers can sign up themselves and get the household role automatically \cite[secs.~Enabling user registration and Using default roles]{keycloak-server-admin-guide}. The realm is saved in infra/keycloak/realm-prepmeup.json, so everyone in the group gets the same setup when they start Keycloak.

\subsection{Test}
The backend has unit tests (NUnit and NSubstitute) against the Application layer and integration tests that start the whole API. The clients are tested with Vitest. GitHub Actions runs all of it on every pull request, and a pull request cannot be merged unless it is green.

\subsection{Tools}
Locally, one docker compose command starts the API, the database and Keycloak. It works the same on Windows and Linux. In production we deploy with Coolify on a server one of us owns (section~\ref{sec:deployment}). We use GitHub for the code and CI and a self-hosted Kaneo as task board.

\section{Backend Architecture}
\label{sec:backend}
The backend is one ASP.NET Core Web API. It serves both user interfaces and will also run the scheduler. Here we describe how the code inside it is split up.

\subsection{Four Layers}
A layered architecture splits the code into layers stacked on top of each other, where a layer may only use the layers below it. The idea is to keep things apart, so a layer can be changed or tested on its own \cite[ch.~3]{microsoft-application-architecture-guide}. We have four layers, and each one is a separate project in the solution:
\begin{center}
\begin{tabular}{@{}p{3.6cm} p{5.3cm} p{5.3cm}@{}}
\textbf{Project} & \textbf{Does} & \textbf{Does not} \\
\hline
Api & Routing, input validation, mapping between contracts and domain, status codes, authorization & Business rules. Talking to the database directly \\
\hline
Application & Runs the use cases and defines the repository interfaces and transactions & Knowing about HTTP, controllers, EF Core or SQL \\
\hline
Domain & Entities and rules: household composition, water need, package content, expiry & Referencing any other project \\
\hline
Infrastructure & EF Core configuration, queries, migrations & Making decisions. It only reads and writes \\
\hline
\end{tabular}
\end{center}
The scheduler is placed in the Api project because it runs in the same process. It calls the same use cases as the controllers, so a delivery is planned by the same rules no matter if a user or the scheduler starts it. Things like authentication, logging and error handling are set up once in Program.cs and are not part of any one layer.

\subsection{Which Way the Dependencies Point}
In the usual layered design, the data access layer is at the bottom, so the business logic depends on it \cite[ch.~5]{microsoft-application-architecture-guide}. We turned that last dependency around. Api uses Application, and Application uses Domain. Application defines the interfaces it needs, for example a repository for households, and Infrastructure implements them with EF Core. Api only knows about Infrastructure at startup, where the implementations are registered in dependency injection.

This is the Dependency Inversion Principle: the part with the business rules should not depend on the part with the technical details, and both should depend on an interface \cite[ch.~4, pp.~139--141]{freeman-head-first-design-patterns}. For us, the rule is when a household needs a new delivery, and the detail is that the items are stored in SQL Server. Goldman calls this structure Clean Architecture \cite[sec.~8.4.1]{goldman-maui-in-action}.

\subsection{Why Domain Has No References}
The Domain project has no project references and no NuGet packages. That means the most important rules in the product (how much water a household needs, what goes in a package, when an item expires) are plain C\# classes. We can test them by creating a household in a unit test and checking the result, without a database or anything to fake. Goldman describes this as a strict rule in Clean Architecture \cite[sec.~8.4.2, p.~262]{goldman-maui-in-action}.

A nice side effect is that the compiler checks it for us. Domain does not reference EF Core, so if someone tries to use EF Core in Domain, the build fails. This is also why we map entities to tables with EF Core's Fluent API in Infrastructure instead of attributes on the entities \cite[sec.~4.3.3]{desanctis-web-apis-aspnet-core}.

The test projects follow the same structure. The unit tests use Application and Domain and replace the repositories with NSubstitute fakes, and the integration tests start the whole API.

\subsection{Alternatives}
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
One Web API project & Least code. Controllers talk to the database directly. & Business rules end up in the controllers, cannot be tested without a database, and the scheduler would need its own copy. \\
\hline
Normal layers (Api, business, data) & The structure most of us know. & The business layer depends on EF Core, so testing it still needs a database or a fake EF Core. \\
\hline
Layers with the data dependency turned around & Domain has no technical details and can be tested without a database. The compiler checks the layers. & Four projects and extra interfaces for a small system. Every new table means an entity, a configuration, a repository and an interface. \\
\hline
\end{tabular}
\end{center}
We went with the last option. It does give more files, but they are the same kinds of files every time, and we always create them in the same order, starting with Domain. The expiry and reorder rules are where we are most likely to make mistakes, so we wanted to be able to test those on their own.

\section{Choice of Client Technologies}
\label{sec:clients}
We have two kinds of users. Customers use an app on their phone, and administrators use a web page on a computer to send out deliveries. According to the requirements, the customer app must run on Android in version 1.0, and the admin interface must be a web application (appendix 1.2).

\subsection{Customer App}
At the meeting on 15-09 we decided to build the customer app with Expo. The course teaches .NET MAUI for native apps and React for the web, so we compared those two with Expo, which is built on React Native.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
.NET MAUI & Taught in the course. Same language as the backend (C\#). Builds apps for Android, iOS and Windows \cite[sec.~1.2]{goldman-maui-in-action}. & The admin panel would still be React, so we would have two UI frameworks, two languages and two test tools. \\
\hline
Only a React web app & Taught in the course. One framework for both user interfaces. & Not an Android app, which the requirements ask for. \\
\hline
Expo (React Native) & Same React, hooks and TypeScript as the admin panel. Builds an Android app and can also run on the web. File-based navigation with Expo Router. & Not in the course. React Native uses native views instead of HTML, so not everything we know about the DOM and CSS applies. \\
\hline
\end{tabular}
\end{center}

We chose Expo. React does not care where it renders: React DOM renders to the browser and React Native renders to the phone \cite[sec.~1.5.1, pp.~16--17]{mardan-react-quickly}. So components, state and hooks work the same way in both of our apps, and everyone in the group can work on both. With MAUI we would have split the group into a C\# half and a React half.

In Expo Router each file in the app folder is a screen \cite{expo-router-introduction}. It works like React Router, except the routes come from the files.

\subsection{Admin Panel}
The admin panel is a normal React app built with Vite, and it uses React Router for navigation \cite[ch.~13]{mardan-react-quickly}.
One thing we need to remember when we deploy it: the web server has to return the same page for every URL, otherwise a user who opens a sub page directly gets a 404 \cite[sec.~13.2.3]{mardan-react-quickly}.

\subsection{Why Two Apps}
Since Expo can also build for the web, one app could in theory be used by both customers and administrators. We decided not to do that. The two users need different screens and have different roles, so a shared app would need role checks on every screen, and the admin screens would end up inside the customer app. The admin panel only has to run in a browser, and for that a plain React app with Vite is simpler than React Native running on the web. Having two apps also means each has its own Keycloak client (section~\ref{sec:auth}).

The downside is two apps to maintain. To keep that manageable they share everything that is not UI: the API client, the TypeScript setup and the npm workspace.

\subsection{The Generated API Client}
Both apps call the API through packages/api-client, which NSwag generates from the API's OpenAPI document. Goldman uses NSwag in the same way for a .NET client and points out that it pays off more as the API grows \cite[sec.~8.3, p.~255]{goldman-maui-in-action}.

For us the main benefit is that the apps do not have to build URLs, handle JSON or write their own types for the data. A screen just calls a method on the client and gets typed objects back. When the API changes we regenerate the client, and if an app still uses something that was removed, the type check in CI fails instead of the app crashing later. The login token is added in one place: each app gives the client a function that returns its token, so the generated code does not need to know anything about Keycloak. Business rules stay in the backend, and the apps only show what the API returns.

\subsection{Testing the Clients}
Both apps are tested with Vitest, which runs the tests in jsdom instead of a real browser \cite{vitest-test-environment}, and React Testing Library \cite{testing-library-react-intro}. The tests are in a tests/ folder in each app and run in CI.

In the admin panel we render components and check what the user sees, for example that the dashboard shows its heading. The customer app is harder, because React Native cannot run in Vitest. We work around it by using React Native for Web in the tests, so the components render as HTML. This means we test logic and state, but not how the screen actually looks on a phone.

The tests never call the real API. We replace the API client with a fake that returns fixed data, so we can test both the list of items and the error message. Navigation is tested the same way with a fake router. What we cannot test like this is how the app looks on Android and the login with Keycloak. We check those by hand on a phone and in the acceptance test (appendix 6.1).

\section{Choice of Authentication}
\label{sec:auth}
Both customers and administrators need to log in. At the meeting on 15-09 we agreed to use an external login provider, and the options we came up with were Firebase, Keycloak, Clerk and OAuth. We also looked at what the course shows, which is ASP.NET Core Identity with our own JWTs.

OAuth turned out not to be an option on its own. OAuth 2.0 is a standard for how an app gets a token, and OpenID Connect adds login on top of it \cite[sec.~8.1.2]{goldman-maui-in-action}. Keycloak implements both, so the actual choice was between the services.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
ASP.NET Core Identity with own JWT & Taught in the course \cite[sec.~9.2]{desanctis-web-apis-aspnet-core}. Everything stays in our own API. & We would have to write login, token refresh, password reset and email verification ourselves. Not an external provider. \\
\hline
Firebase Authentication & Hosted by Google, quick to start with, good mobile SDKs. & User data is stored at Google. Roles need extra setup. Made for the rest of Firebase, which we do not use. \\
\hline
Clerk & Hosted, with ready-made login screens for React and Expo. & User data is stored at a third party. Costs money above the free tier. Hard to move away from. \\
\hline
Keycloak & Open source and free. Runs in our own compose. Uses standard OpenID Connect, so the API only needs normal JWT validation. Has roles built in. & Heavier to run (Java) and more to set up. We have to run and update it ourselves. Only mentioned briefly in the course. \\
\hline
\end{tabular}
\end{center}

We chose Keycloak, mostly because we already host everything else ourselves. Kaneo, the API and the database all run on our own server, so Keycloak is just one more container. It also means that customers' names, addresses and household information do not end up at Google or another company, which makes GDPR simpler.

Another reason is that the apps log in with a standard flow (Authorization Code with PKCE, which is what is recommended for mobile and browser apps \cite[sec.~2.1.1]{ietf-rfc9700-oauth-security-bcp}), and the API only checks a normal JWT. If we ever switch provider, the API code does not change much. Logging in by sending the password directly through the app is turned off \cite[sec.~2.4]{ietf-rfc9700-oauth-security-bcp}. Finally, the household and admin roles are put into the token \cite[sec.~Role scope mappings]{keycloak-server-admin-guide}, so the API can use them. Keycloak stores them in a different claim than ASP.NET Core expects, so we have to map them before role checks work.

The price is that Keycloak takes more work to set up and uses more memory than the API itself. We think that is fine, because the realm file makes the setup the same for everyone, and learning to use a real login provider is something we want to get out of the project.

\section{Choice of Deployment}
\label{sec:deployment}
At the same meeting we agreed that we need one shared deployment. Once there is an administrator sending out deliveries, everyone has to use the same data, and that does not work if each of us only runs the system on our own computer.

\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
Only local & Nothing to set up. & No shared data, no real administrator, and no testing on a phone outside the home network. \\
\hline
Azure & Used in the course. Managed services. & Costs money or student credits that run out. Many services to set up. \\
\hline
Coolify on own server & Free, because the server already exists. Deploys directly from docker compose and handles HTTPS certificates \cite{coolify-traefik-overview}. & Depends on one server and one group member. Not in the course. \\
\hline
\end{tabular}
\end{center}

We chose Coolify. The production setup has its own compose file, which is a bit different from the local one. No ports are opened, because Coolify's proxy handles HTTPS and forwards traffic to the containers. Keycloak runs in production mode with its own PostgreSQL database, so user accounts are kept separate from the application data. All URLs and passwords come from environment variables in Coolify, and the stack does not start if one of them is missing.

\section{Choice of Data Access and Database}
\label{sec:data}

\subsection{EF Core}
We looked at two ways to use a SQL database from .NET: EF Core, which is a full ORM \cite[sec.~4.3]{desanctis-web-apis-aspnet-core}, and Dapper, where you write the SQL yourself and Dapper turns the result into objects \cite{dapperlib-dapper}.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
EF Core & Queries are written in LINQ. Tracks changes, so everything can be saved in one transaction. Creates the schema and migrations from the C\# classes. & More to learn. The generated SQL can be slow for complex queries and bulk inserts. \\
\hline
Dapper & Full control over the SQL. Very fast. & No change tracking and no schema generation. All SQL and all schema changes are written by hand and kept in sync with the classes by hand. \\
\hline
\end{tabular}
\end{center}

We chose EF Core. Dapper makes sense when you need full control over the SQL or performance really matters. Performance is its main feature \cite{dapperlib-dapper}, while an ORM hides the SQL and adds some overhead \cite[sec.~4.3.1]{desanctis-web-apis-aspnet-core}. That is not our situation. We have a small amount of data, and the heaviest query (finding items close to expiry) runs in the background, so no user is waiting for it. Change tracking is actually useful for us, because when a delivery is created, both the delivery and the household's items change, and they have to be saved together \cite[sec.~4.3.4]{desanctis-web-apis-aspnet-core}. With EF Core the C\# classes are also the only description of the database, where Dapper would give us classes, SQL and migration scripts to keep in sync.

If a query gets slow later, EF Core lets us write that one query in raw SQL \cite{microsoft-efcore-sql-queries}. Since the data access is behind the repository interfaces, such a change stays inside Infrastructure.

\subsection{Migrations}
If a database is changed by hand, or the scripts are not in version control, the databases on different machines slowly drift apart and things break when the app runs. A change one of us makes to the schema has to be something the others can run on their own database \cite{dbup-philosophy}. So we knew we wanted migrations. The question was which kind.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
EF Core Migrations, code first & Generated from the classes, so classes and schema match. Can be rolled back and reviewed in the pull request. & The generated SQL has to be checked. For example, a rename can be generated as drop and add, which deletes the data. \\
\hline
DbUp with SQL scripts & Plain SQL that is easy to read. & Classes and schema updated by hand. \\
\hline
Database first & Good if a database already exists. & There is no existing database, and we want the domain to decide the schema. \\
\hline
Only create the schema at startup & No migration files. & Only works on an empty database, so the schema cannot be changed later. \\
\hline
\end{tabular}
\end{center}
The table is based on \cite[secs.~4.3.2 and 4.3.5]{desanctis-web-apis-aspnet-core}, \cite{microsoft-efcore-managing-migrations}, \cite{microsoft-efcore-create-drop-apis} and \cite{dbup-docs}.

We chose EF Core Migrations with code first. The schema is only changed through a new migration, never by hand, and the migration is committed in the same pull request as the change to the classes, so the reviewer can see the SQL. In production the migrations run as a migration bundle before the new API starts \cite[sec.~12.4.4, p.~421]{desanctis-web-apis-aspnet-core}. The steps are described in appendix 10.3.

\subsection{SQL Server}
Our data has a lot of relations: a household has members and items, an item points to a product in the catalogue, and a delivery has lines that point to items. It is also important that a delivery and the change to the household's items are saved together. Transactions and foreign keys are exactly what relational databases are good at \cite[secs.~4.1 and 4.1.1]{desanctis-web-apis-aspnet-core}.
\begin{center}
\begin{tabular}{@{}p{3.1cm} p{5.6cm} p{5.6cm}@{}}
\textbf{Option} & \textbf{For} & \textbf{Against} \\
\hline
SQL Server & Used in the course, so the slides and exercises apply directly. Works well with EF Core. Runs in Docker. & Big image. The free versions have limits. \\
\hline
PostgreSQL & Free and light. Works well with EF Core. We already use it for Keycloak. & Not used in the course. Nothing in our requirements needs it. \\
\hline
MongoDB & Flexible schema. Can scale to several servers. & No foreign keys, so the app has to keep track of the relations \cite{mongodb-data-consistency}. We have many relations and one server. \\
\hline
\end{tabular}
\end{center}

We chose SQL Server, mainly because it is what the course uses, and PostgreSQL did not give us anything we needed. Because of the layers, the choice only shows up in Infrastructure, so switching later would mean a new EF Core provider and new migrations, but no changes to the rules or the API \cite[secs.~4.1.2 and 4.3.1]{desanctis-web-apis-aspnet-core}.

\subsection{Database in Tests}
The unit tests do not use a database, since they test Domain directly and Application with fake repositories. For integration tests we use an in-memory SQLite database, where each test gets its own database and no server is needed \cite{microsoft-efcore-testing-strategy}. The catch is that our migrations are made for SQL Server, so the SQLite tests have to create the schema in another way. That means the integration tests do not test our migrations, and SQLite does not behave exactly like SQL Server, which Microsoft's guide also warns about. We think that is acceptable, because the migrations are still run against SQL Server both locally and when we deploy.

\section{Version Control and Git Workflow}
\label{sec:git}
The code is on GitHub. The course uses GitLab CI, but the ideas are the same, so we use GitHub Actions. Coolify also gets the production compose file and the images from GitHub.

We looked at three workflows: trunk-based development \cite{hammant-trunk-based-development}, GitHub Flow \cite{chacon-github-flow-2011} and Git Flow \cite{driessen-git-branching-model}. We chose GitHub Flow. Driessen, who came up with Git Flow, recommends a simpler workflow like GitHub Flow for teams that deliver a web application continuously and only have one version running \cite{driessen-git-branching-model}. That is us. Git Flow is made for software with planned versions and several versions in use at once, so its extra branches would not help us. Pure trunk-based, where everyone commits directly to the main branch, would mean no code review before merge, and we want that.

In practice:
\begin{itemize}
    \item The main branch is the only long-lived branch and should always be deployable.
    \item We work on short branches that start with the type of change and the number of the Kaneo task, for example feat/pmu-12-household-profile.
    \item Commit messages follow Conventional Commits, for example feat(api): add household endpoint.
    \item Everything goes into the main branch through a pull request with green CI and one review. We squash merge, so each pull request becomes one commit.
    \item At the end of a sprint we tag a release on the main branch, for example v0.1.0.
\end{itemize}
Branch names and commit messages are checked by git hooks locally and again in GitHub Actions. See appendix 10.1.

\section{Operations, CI and Security}
\label{sec:ops}
Here we explain the choices we made about running the system and keeping it secure, and what we know is still missing. The exact deployment steps and how to roll back are in appendix 10.3.

\subsection{Containers}
Every service runs in a Docker container, both locally and in production. The API image is built in two steps with a multi-stage build \cite{docker-multi-stage-builds}\cite{microsoft-aspnetcore-docker}: first the code is built with the .NET SDK, and then only the finished files are copied into a smaller runtime image. That way the SDK and the source code are not in the image we run. The API also runs as a normal user instead of root, so a bug in the API does not give an attacker root in the container.

Our Keycloak image is the official one with our realm file copied in. One thing we learned is that Keycloak only imports the realm the first time \cite[sec.~Importing a realm during startup]{keycloak-import-export}. After that, changes to the file do not reach the running Keycloak, so they also have to be made in the admin console.

In production we use fixed image versions instead of latest, so a new version cannot sneak into production without a commit.

\subsection{CI and Deployment}
The CI workflow first builds and tests the backend and the apps. If everything is green on the main branch, it builds the images, pushes them to GitHub Container Registry and tells Coolify to deploy them. A second workflow checks branch names and pull request titles.

Continuous integration means integrating often and checking every integration with an automated build that runs the tests \cite{fowler-continuous-integration}. We have also made the pipeline the only way into production. If a test fails, no image is built and nothing is deployed, and automatic deployment is turned off in Coolify, so there is no way around it. Production also runs the exact image that was tested, because Coolify does not build anything itself.

We had a bug in the deploy job at first. It only failed if Coolify answered with an error, so when Cloudflare answered with a redirect, the job was green even though nothing was deployed. Now the job only passes if Coolify answers 200. More about this in appendix 10.3.

\subsection{Network and HTTPS}
Only Coolify's proxy can be reached from the internet. It handles HTTPS and forwards the requests to the API and Keycloak inside the Docker network. In this setup only the proxy needs a certificate \cite{microsoft-kestrel-reverse-proxy}. No container opens a port in production, so the databases can only be reached from inside the network (see appendix 3.1). The traffic inside the network, for example between the API and SQL Server, is not encrypted. We accept that because it never leaves the server.

\subsection{Login in the API}
The API checks every token it gets: it must be signed by Keycloak, come from the right issuer, be meant for our API and not be expired \cite[sec.~9.2.5]{desanctis-web-apis-aspnet-core}\cite[secs.~4.1.1, 4.1.3, 4.1.4 and 7.2]{ietf-rfc7519-jwt}. Tokens are valid for 15 minutes, since the advice is to keep them short \cite[sec.~9.1.2]{desanctis-web-apis-aspnet-core}.

In production the API talks to Keycloak over the internal network, but the tokens contain Keycloak's public address. Because the two addresses are different, we had to set the expected issuer by hand. Chapter 8 in the report describes how we found this. For the same reason the API is allowed to fetch Keycloak's settings over plain HTTP inside the network. Microsoft recommends only doing that in development \cite{microsoft-jwtbearer-requirehttpsmetadata}, so it only works because the traffic stays internal.

The requirements NFR-09 to NFR-11 say what the API must refuse. A request without a token gets 401 (NFR-11). Customers must get 403 on admin endpoints (NFR-10), which needs a role check on those endpoints. A household must only see its own data (NFR-09). A role cannot solve this, so the API has to compare the household in the request with the user in the token. We put that check in the Application layer, so it cannot be forgotten in a single controller.

CORS only allows our two apps. That is not real protection, though, because CORS is only enforced by browsers \cite[sec.~3.1.1]{desanctis-web-apis-aspnet-core}. The API still has to check authorization itself.

\subsection{Secrets}
Passwords and other secrets are only set as environment variables in Coolify, not in the repository or the images \cite[sec.~12.1.4]{desanctis-web-apis-aspnet-core}\cite{microsoft-aspnetcore-app-secrets}. That is why our images on GitHub can be public. If a secret is missing, the stack refuses to start instead of starting with an empty password. GitHub only stores the Coolify webhook and a token that can start a deployment and nothing else, and images are pushed with the temporary token GitHub Actions creates for each run.

\subsection{Known Weaknesses}
These are things we know are not good enough yet. They are also listed under open decisions.
\begin{itemize}
    \item The API logs in to SQL Server as sa. It should have its own user that can only read and write data.
    \item If the Keycloak address is missing from the configuration, the API starts without authentication. That cannot happen in production because the compose file requires it, but the API should refuse to start (NFR-07).
    \item An API should only accept HTTPS. A redirect from HTTP is not enough for an API, because the token may already have been sent in clear text \cite[sec.~HSTS and API projects]{microsoft-aspnetcore-enforce-https}. We have not checked yet how Coolify's proxy handles this.
    \item The GitHub Actions we use are pinned to a version like v4, not to a specific commit. If one of them is hacked, our pipeline would run the new code \cite[sec.~Using third-party actions]{github-secure-use}.
\end{itemize}

\section{Key Technical Decisions}
\begin{itemize}
    \item One backend serves both user interfaces, and the OpenAPI document is the contract.
    \item Business rules are only in Domain. The apps call the API through the generated client.
    \item EF Core instead of hand-written SQL.
    \item The database cannot be reached from outside Docker.
    \item No MediatR. It solves a problem we do not have and is not part of the course.
    \item We build one feature at a time through all four layers, starting with Domain.
    \item All text the user sees is in English, and there is no translation (NFR-01).
\end{itemize}

\section{Open Decisions}
\begin{itemize}
    \item How the customer app fetches data and stores the token, for example with TanStack Query and Expo SecureStore.
    \item Whether the customer app should also be released as a web app.
    \item A separate database user for the API instead of sa.
    \item Make the API refuse to start without a Keycloak address outside development.
    \item Check that Coolify's proxy does not serve the API over plain HTTP, and that Keycloak and the admin panel redirect to HTTPS.
    \item Whether to pin GitHub Actions to specific commits.
    \item Use SQL Server Express in production instead of Developer (section~\ref{sec:data}).
    \item Make the image tag required in Coolify, so production cannot fall back to the newest image.
    \item Map Keycloak's roles to ASP.NET Core roles before the first role check (NFR-10).
\end{itemize}
