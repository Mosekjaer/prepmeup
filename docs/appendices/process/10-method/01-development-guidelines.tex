\section{Local Setup}
You need the .NET 10 SDK, Node.js and Docker.

\begin{lstlisting}
dotnet build                 # build the backend
dotnet test                  # run unit and integration tests
docker compose up            # start api, db and keycloak

cd clients
npm install                  # install all client packages (also activates git hooks)
npm test                     # Vitest in all client packages
npm run typecheck            # tsc in all client packages
npm run generate:api-client  # regenerate api-client from the OpenAPI document
\end{lstlisting}

When compose is running, the API is on port 5001 and Keycloak on port 8082 on \texttt{localhost}.

\section{Configuration and Secrets}
\begin{itemize}
    \item Passwords and other secrets are never committed. They are set as environment variables or in a local \texttt{.env} file, which is ignored by git.
    \item \texttt{.env.example} shows which variables exist. Locally you need at least \texttt{MSSQL\_SA\_PASSWORD} and \texttt{KEYCLOAK\_ADMIN\_PASSWORD}.
    \item In production the variables are set in Coolify. \texttt{docker-compose.prod.yml} stops with an error if one is missing, so we do not deploy with an empty password by accident.
\end{itemize}

\section{Git Workflow}
We use GitHub Flow. Why we chose it is described in appendix 2.1.

\subsection{Branches}
\texttt{main} is the only long-lived branch, and it must always work. All work happens on a short-lived branch created from an up-to-date \texttt{main}:
\begin{lstlisting}
git switch main
git pull
git switch -c feat/pmu-12-household-profile
\end{lstlisting}

A branch name is \texttt{<type>/<slug>}. The slug is lowercase English words separated by hyphens, and starts with the Kaneo task number when there is one. A branch should live for days, not weeks.

\subsection{Types}
The same types are used for branches and commits:

\begin{center}
\begin{tabular}{@{}l l@{}}
\textbf{Type} & \textbf{Used for} \\
\hline
\texttt{feat} & a new feature \\
\texttt{fix} & a bug fix \\
\texttt{refactor} & restructuring code without changing behaviour \\
\texttt{test} & only tests \\
\texttt{docs} & report, appendices and other documentation \\
\texttt{style} & formatting only \\
\texttt{perf} & performance improvement \\
\texttt{build} & build setup and dependencies \\
\texttt{ci} & GitHub Actions \\
\texttt{chore} & other maintenance \\
\texttt{revert} & undoing an earlier commit \\
\end{tabular}
\end{center}

\subsection{Commit Messages}
We follow Conventional Commits. The first line is \texttt{<type>(<scope>): <description>}, in English, in the imperative (``add'', not ``added''), and at most 72 characters. The scope is optional.
\begin{lstlisting}
feat(api): add household profile endpoint
fix(mobile): show error when the API is unreachable
docs: update technical analysis
\end{lstlisting}

\subsection{Pull Requests}
\begin{itemize}
    \item Keep the branch up to date with \texttt{git merge origin/main}. We do not rebase or force push branches that others may have pulled.
    \item Open a pull request against \texttt{main}. The title must also follow Conventional Commits, and the description links the Kaneo task.
    \item The pull request needs green CI and one review from another group member before merge.
    \item We use squash merge. The whole branch becomes one commit on \texttt{main}, with the pull request title as the message. The branch is deleted afterwards.
\end{itemize}

\subsection{Releases}
At the end of a sprint, or before a hand-in, we put a tag on \texttt{main}, for example \texttt{v0.1.0}. We do not use release branches.

\subsection{Automatic Checks}
The rules are checked automatically, so nobody has to remember them all:
\begin{itemize}
    \item \texttt{.githooks/commit-msg} rejects a commit whose message does not follow the format.
    \item \texttt{.githooks/pre-push} rejects a push directly to \texttt{main} and a push of a branch with a wrong name.
    \item The hooks are turned on by \texttt{npm install} in \texttt{clients/}. Without Node.js, run this once instead:
\begin{lstlisting}
git config core.hooksPath .githooks
\end{lstlisting}
    \item The GitHub Actions workflow \texttt{conventions.yml} checks the branch name and pull request title again on GitHub, where it cannot be skipped.
    \item All three use the same script, \texttt{.githooks/check-conventions.sh}, so the rules are only written in one place.
\end{itemize}

    \item Kaneo tasks: Danish.
\end{itemize}

\section{AI Tools}
\begin{itemize}
    \item The shared rules for the AI tools are in \texttt{AGENTS.md} in the repository root. Change a rule there, not in a tool-specific file.
    \item The AI may read the Kaneo board, create and comment on tasks, create labels, and set the due date of a task to the last day of its sprint. New tasks from the AI go to the backlog. Moving, assigning, estimating and deleting tasks is done by the group.
    \item The AI cannot read \texttt{.env} files or key files.
    \item Whoever commits code must be able to explain it, also at the exam.
\end{itemize}

\section{Sprints and the Kaneo Board}
A sprint is two weeks, from Wednesday to the Tuesday two weeks later. Sprint review, retrospective and planning are held on the same day, and the sprint goal is written in the minutes of that meeting.

\begin{center}
\begin{tabular}{@{}ll@{}}
Sprint & Period \\ \hline
1 & 16/9 -- 29/9 \\
2 & 30/9 -- 13/10 \\
3 & 14/10 -- 27/10 \\
4 & 28/10 -- 10/11 \\
5 & 11/11 -- 24/11 \\
6 & 25/11 -- 8/12 \\
\end{tabular}
\end{center}

The report is handed in on Friday 11/12. The days from 9/12 to 11/12 are not a sprint.

\begin{itemize}
    \item The Backlog view in Kaneo is the product backlog. The board is the sprint backlog.
    \item A task moves from the backlog to \emph{To Do} at sprint planning, and only when it is ready: it has a description that starts with the requirements it covers (\texttt{Krav: FR-xx}), a definition of done, a story point label, an epic label and an owner.
    \item Every task in a sprint gets the label of that sprint. A task that is not finished keeps its label and gets the next one as well, so spillover is visible.
    \item Story points use the planning poker scale: 0, \textonehalf, 1, 2, 3, 5, 8, 13, 20, 40 and ?. The group estimates together.
    \item Epic labels follow the grouping of the user stories in the requirements specification: Account, Household, Subscription, Notifications, Catalogue and Dispatch. Work that is not a requirement gets \emph{Teknisk} or \emph{Rapport}.
\end{itemize}

\section{Definition of Done}
A task is done when:
\begin{itemize}
    \item \texttt{dotnet build} and \texttt{dotnet test} are green, and the client tests if \texttt{clients/} was changed.
    \item The change is merged to \texttt{main} through a pull request with green CI and one review.
    \item The Kaneo task is linked in the pull request.
    \item The person who made the change can explain it.
\end{itemize}

What happens after the merge --- the image build, the deployment to production and the rollback procedure --- is described in appendix 10.3.
