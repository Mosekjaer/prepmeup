\section{Overview}
PrepMeUp runs as a set of Docker containers started with docker compose. There are two setups, each with its own compose file: one for local development and one for production on our server with Coolify. In both, all containers are on the same Docker network and find each other by service name, for example db and keycloak. Why we chose Keycloak and Coolify is described in appendix 2.1.

The two clients are not containers in compose. The customer app runs on the phone, and the admin panel runs in the browser. Both talk to the API over HTTP(S), and both send the user to Keycloak to log in.

The database has no host port, so only the API can reach it. The API waits until the database health check passes before it starts. Keycloak imports our realm file at startup. The admin panel (Vite, port 5173) and the Expo app (port 8081) run outside Docker, and the API's CORS policy allows these two addresses. The data from the database and Keycloak is kept in two Docker volumes.

\subsection{Token Validation}
The browser and the phone reach Keycloak on port 8082 on localhost, but inside Docker the API reaches it by its service name on port 8080. The token says it was issued by the localhost address, so the API is configured with two addresses. The first is the public address, which must match the issuer in the token. The second is the internal address, where the API fetches Keycloak's configuration and signing keys.

No container publishes a port. Coolify's reverse proxy receives the traffic from the internet on HTTPS and forwards it to the API and Keycloak on port 8080 inside the network. Because HTTPS ends at the proxy, Keycloak reads the forwarded headers to know the original address and scheme. The two databases can only be reached from inside the network.

The public URLs of the admin panel, the customer app and Keycloak are set as environment variables in Coolify. The same variables are used for the API's CORS policy and the redirect addresses in the Keycloak realm. All services are set to restart, so they start again after a crash or a server restart.

\section{Login Flow}
Both clients log in with the Authorization Code flow with PKCE \cite{ietf-rfc6749-oauth2,ietf-rfc7636-pkce}. Figure~\ref{fig:auth-flow-mobile} shows the flow for the customer app. The text on each arrow is the request or response that is sent.

\drawiofig[\linewidth]{auth-flow-mobile}{Login in the customer app. The user's password only goes between the browser and Keycloak.}{fig:auth-flow-mobile}

The flow has four parts:
\begin{enumerate}
    \item \textbf{Discovery.} When the app starts, it reads Keycloak's discovery document \cite{openid-connect-discovery}. It gets the addresses of the login page, the token endpoint and the logout endpoint from there, so they are not hardcoded in the app.
    \item \textbf{Login in the browser.} The app makes a random code verifier and sends only its SHA-256 hash, the code challenge, to Keycloak. The login page opens in the system browser (a Custom Tab on Android) and not inside the app, as RFC 8252 recommends for native apps \cite[sec.~8.12]{ietf-rfc8252-native-apps}. The user types email and password into Keycloak's own page. The app never sees them.
    \item \textbf{Back to the app.} Keycloak redirects to \texttt{prepmeup://auth/callback} with a short-lived code and the same state value the app sent. The operating system gives the redirect to the app because the app owns the \texttt{prepmeup} scheme \cite[sec.~7.1]{ietf-rfc8252-native-apps}. The app checks the state and sends the code and the original code verifier to the token endpoint. Keycloak hashes the verifier and compares it with the challenge from step 2. Someone who steals the code cannot use it without the verifier \cite[sec.~1]{ietf-rfc7636-pkce}.
    \item \textbf{Calling the API.} Keycloak returns an access token (a JWT, valid for 15 minutes) with \texttt{prepmeup-api} as audience. The app sends it in the \texttt{Authorization: Bearer} header \cite[sec.~2.1]{ietf-rfc6750-bearer}. The API fetches Keycloak's public signing keys once and caches them. After that it checks every token locally: signature, issuer, audience and expiry \cite{ietf-rfc7519-jwt}. It then turns the roles in \texttt{realm\_access.roles} into role claims, so the \texttt{AdminOnly} policy works. A missing or invalid token gives 401, a valid token without the admin role gives 403 on admin endpoints.
\end{enumerate}

So the credentials only travel between the browser and Keycloak. The API only ever sees the token. This is what the supervisor asked for at the meeting on 6/10.

The app also receives an ID token and a refresh token. The ID token is only used to log out. The refresh token is not used yet, so the user has to log in again when the access token runs out.

\subsection{Admin Panel}
The admin panel will use the same flow with its own Keycloak client, \texttt{prepmeup-admin}, which is already in the realm. The only differences are that the redirect goes to the admin panel's web address instead of the app scheme, and that the browser calls the token endpoint from JavaScript, so Keycloak must allow the admin panel's origin. The login is not built yet (PMU-76), so this part is not shown in a diagram.

\subsection{What Was Checked}
The first half of the flow was checked in the browser against the local stack. The request to the login page had \texttt{response\_type=code}, \texttt{code\_challenge\_method=S256} and \texttt{scope=openid}, and the redirect back had \texttt{code}, \texttt{state}, \texttt{session\_state} and \texttt{iss}. The token request and the API call in the figure are drawn from the code in \texttt{clients/apps/mobile/src/lib/auth.tsx} and \texttt{src/PrepMeUp.Api/Program.cs}, and have not been checked in Chrome DevTools yet.
