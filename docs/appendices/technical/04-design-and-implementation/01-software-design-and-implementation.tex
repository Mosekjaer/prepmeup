\section{Roles and Claims}
This section describes how the API tells a customer from an administrator (NFR-10). The login flow itself is in appendix 3.1.

\subsection{Realm Roles}
We have two roles: household and admin.
\begin{itemize}
    \item A household is a customer who owns a household and a subscription.
    \item An admin is someone who works in the admin panel.
\end{itemize}

\textbf{How a user gets a role}

Every new user gets the household role automatically, and only an admin can give someone the admin role.
So plainly put: a household is only a household, whereas an admin is a household \textit{and} an admin.

Note that we will create the first admin in the system manually. After the system's release, new admins can only be added by an existing admin.

\textbf{Choice of role types from Keycloak}

Keycloak has two kinds of roles.
\begin{itemize}
    \item A realm role belongs to the whole realm, so every app in it sees the same role.
    \item A client role belongs to one app only \cite{keycloak-server-admin-guide}.
\end{itemize}
We have chosen to use realm roles because:
\begin{itemize}
    \item The roles say what a person is, not which app they are using.
    \item The API does not need to know which app a token came from to decide if a request is allowed.
\end{itemize}

\textbf{Risk}

There is a risk we accept: both apps are public clients, and their tokens are meant for the same API. A customer can therefore log in through the admin panel and get a valid token. What \textit{stops} them is the admin role, which the API checks on every admin endpoint and answers with 403 (NFR-10). The admin panel should also send users without the role away, but that is only for the user's benefit. It is not what keeps the data safe.

\textbf{How the role appears in the token and how the API reads it}

Keycloak puts the realm roles in the token as a list called roles inside a claim called realm\_access. ASP.NET Core does not understand this format, so a check like "is this user an admin" would always fail. We therefore have a claims transformation in the API that runs on every authenticated request:
\begin{itemize}
    \item It reads the list of roles from the realm\_access claim.
    \item It adds each role as an ordinary role claim that ASP.NET Core understands.
    \item It skips roles the user already has, and it does nothing if the claim is missing or cannot be read.
\end{itemize}
After this, the controllers can protect an endpoint with the admin role in the normal ASP.NET Core way, without knowing anything about Keycloak's token format.

\subsection{Onboarding}

\textbf{Onboarding status}

We have chosen that onboarding status is solely stored in the database. So at any point when the Client needs to know the onboarding status of the user, it has to make a call to the API.
We are aware that this causes extra "unnecessary" calls to the database, which hurts performance. However our choice satisfies clean architecture in the sense that data is kept in domain (in backend) \textit{and} that avoid flooding the token with information. This is good for maintainability of our system.

\section{Keycloak decisions}

\textbf{Login library in the admin panel}

The admin panel logs in with react-oidc-context, which is built on oidc-client-ts. It follows the standard OpenID Connect and does not depend on Keycloak. The mobile app also uses standard OpenID Connect, so the two apps differ only in how they redirect and where they keep the token.

\textbf{Where the admin panel keeps the token}

The token is kept in memory only, as in the mobile app, so a script injected into the page cannot read it from browser storage. A reload loses the token. The admin panel then sends the user to Keycloak, which logs them in again without a password as long as the Keycloak session is alive.

\textbf{How the admin panel checks the role}

After login the admin panel calls the admin ping endpoint. A 200 lets the user in and a 403 shows a message that the account has no access. This way only the API knows the rule for who is an admin, and the admin panel does not have to decode the token.

\textbf{Sign-in screen and sign-out}

An unauthenticated user sees a sign-in screen with a sign-in button. Sign-out ends the Keycloak session, as in the mobile app, so a customer who is turned away can sign in with another account.

\textbf{Token refresh}

The client should refresh the access token in the following cases
\begin{itemize}
    \item Shortly before the access token expires.
    \item When the API replies with 401.
\end{itemize}
The admin panel uses the automatic silent renew of react-oidc-context, which uses a refresh token. If the renewal fails or the API replies with 401, the user is sent to the sign-in screen.

\textbf{Tests of the admin login}

We test the admin login with Vitest and mock react-oidc-context and the network, as the mobile app does with expo-auth-session. The tests check that the token is sent to the API, that a 403 shows the message, and that sign-out ends the session. The flow against Keycloak itself is checked by hand.

\section{Keycloak Login flow: Client and admin}

The flowdiagram below shows how login flows for both a regular customer and for an administrator.

flow diagram here

The diagram assumes that the user has opened the client app.
When the app starts, the client app fetches the URL to keycloak's login-page from WHERE?
\begin{enumerate}
    \item In Client, the User (either customer or admin) clicks 'Log in'
    \item Client generates PKCE-values and state and saves them locally. They are:
        \begin{itemize}
            \item code\_verifier: a random string that stays with the client. It is sent later.
            \item code\_challenge: a SHA-256-hash of the code\_verifier. It is sent in step 3.
            \item state: another random string. It is sent as it is in step 3 (non-hashed).
        \end{itemize}
    \item Client builds and opens the login-URL for Keycloaks /auth-endpoint. It attaches (among others) the following values:
        \begin{itemize}
            \item client\_id: a string that is either `prepmeup-mobile' (if login is requested from customer app) or `prepmeup-admin' (if login is requested from admin panel).
            \item redirect\_uri: The address that Keycloak should send the user \textit{back} to.
            \item code\_challenge and state (generated in step 2)
        \end{itemize}
    \item Keycloak shows the login page, \textit{if} client\_id and redirect\_uri are valid. Also, keycloak saves code\_challenge and state for later (see step WHAT), and displays it's own login page.
    \item User types email and password and clicks 'log in'.
    \item Keycloak validerer login-oplysningerne: Er de korrekte?
        \begin{itemize}
            \item Nej: Keycloak viser en fejl på login-siden og bruger forsøger igen.
            \item Ja: Keycloak slår brugerens realm-roller op. Det er 'household' for kunder og 'admin' for administratorer. I trin 12, kommer disse roller med i jwt token.
        \end{itemize}
    \item Keycloak does to things:
        \begin{itemize}
            \item starts a an SSO-session by putting an SSO-cookie in the browser, so that the user is logged in \textit{at keycloak}. As long as the SSO session is up, Keycloak will supply a new access token on a refresh token. The purpose of this, is then the user doesn't have to re-login everytime the jwt token expires.
            \item generates a random and short-lived authorization code. It is used in step 10 to exhange for an access token. This authorization code is bound to the client\_id, redirect\_id and code\_challenge that client sent along in the URL in step 3.
        \end{itemize}
    \item On this step, something happens first on Keycloak-side and then on Client-side:
        \begin{itemize}
            \item Keycloak sends the browser back to redirect\_uri, which was provided by client in url in step 3. It sends back the authorization code and also the state back, which client provided in step 3.
            \item Client recieves the redirect with a state value and the authoriation code.
        \end{itemize}
    \item Client checks that state is the same as what was sent to Keycloak in step 3. This is how the client can tell that the response actually came from Keycloak and not some hacker.
        \begin{itemize}
            \item No: The login-process is stopped and the client doesn't ask keycloak for access token.
            \item Yes: Client continues to step 10.
        \end{itemize}
    \item Client sends a POST http request to Keycloaks token-endpoint. The request contains:
        \begin{itemize}
            \item grant\_type=authorization\_code: This tells keycloak that client would like to exchange \textit{some} code to \textit{some} token.
            \item code: The authorization code. This was recieved from Keycloak in step 9.
            \item code\_verifier: The secret string from step 2 (un-hashed).
            \item same client\_id and redirect\_uri as in step 3.
        \end{itemize}
    \item Keycloak checks the following:
        \begin{itemize}
            \item Is the authorization code even valid? As in unused and not expired?
            \item Are client\_id and redirect\_id the same as in step 3?
            \item Makes a PKCE-check: Keycloak hashes code\_verifier with the SHA-256 algorithm and compares it to code\_challenge, which it saved in step 4. If a hacker has somehow gotten hold of the authorization code in step 8 their request will fail here, because they have at most the code\_challenge, which was the hashed version of code\_verifier, and you cannot calculate backwards from SHA-256-hash \cite[sec.~1]{nist-fips-180-4}.
        \end{itemize}
        Is the request valid?
        \begin{itemize}
            \item No: Keycloak answers client with 400 Bad Request with the error invalid\_grant. The authorization code cannot be reused.
            \item Yes: Keycloak moves on to issue tokens in step 12.
        \end{itemize}
    \item Keycloak issues \textit{three} tokens:
        \begin{itemize}
            \item Access token of type jwt "Json Web Token" signed by keycloak. It contains bl.a. the users UUID, realm-roles (household and/or admin) and \textit{audience} (which is prepmeup-api). This jwt is valid for 15 minutes.
            \item Refresh token, which client can use to get a new access token, when the old one expires \textit{without} having to log in again. This, however, is only possible as long as the SSO-session (started in step 7) lives.
            \item ID token, which tells the client who is logged in. This info is only  used for logout.
        \end{itemize}
    \item Client stores the three recieved tokens in a way that depends if it's mobile-app (for customer) or admin-panel.
    Then the Client registers a function with the api-client that returns the current access token. The effect of this, is that before every request the api-client calls that function and can therefore add a non-expired token to the http request.
        \begin{itemize}
            \item admin-panel: Alle threee tokens are kept in the browsers memory and are lost when the page is reloaded. Admin has to click 'log in' again.
            \item mobile-app: access token and ID token are kept in memory and are lost when the app is closed. The refresh token is saved to persistent storage on the phone, so the user stays signed in when reopening the app.
        \end{itemize}
    \item User is now logged in.
\end{enumerate}
