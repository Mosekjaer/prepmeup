\section{Overview}
PrepMeUp runs as a set of Docker containers started with docker compose. How the containers are set up locally and in production is described in appendix 10.3. This appendix is about how the clients, Keycloak and the API talk to each other, how a user logs in, and how the API checks the token. Why we chose Keycloak is described in appendix 2.1.

The customer app is not a container. It runs on the phone. The admin panel runs in the browser, but in production its files are served from a container (appendix 10.3). Both clients talk to the API over HTTP(S), and both send the user to Keycloak to log in.

\section{Login Flow}
Both clients log in with the Authorization Code flow with PKCE \cite{ietf-rfc6749-oauth2,ietf-rfc7636-pkce}. Figure~\ref{fig:auth-flow} shows the flow as boxes and numbered arrows. The text on each arrow is what is actually sent.

\drawiofig[\linewidth]{auth-flow}{Login flow between the client, Keycloak and the API. The password only goes from the user to Keycloak.}{fig:auth-flow}

The numbers below match the arrows in the figure.

\paragraph{1. Open the login page.} When the user taps sign in, the client makes a random secret called the code verifier. It keeps the secret and sends only its SHA-256 hash, the code challenge, to Keycloak together with its client id, its redirect address and a random state value. The login page opens in the system browser and not inside the app, as recommended for native apps \cite[sec.~8.12]{ietf-rfc8252-native-apps}. The client finds Keycloak's addresses in Keycloak's discovery document, so they are not hardcoded \cite{openid-connect-discovery}.

\paragraph{2. Type the password.} The user types email and password into Keycloak's own page. The client never sees them.

\paragraph{3. Back to the client.} Keycloak sends the browser back to the redirect address with a one-time code and the same state value. The client checks that the state matches what it sent.

\paragraph{4 and 5. Swap the code for a token.} The client sends the code and the code verifier from step 1 to Keycloak's token endpoint. Keycloak hashes the verifier and compares it with the challenge. Someone who steals the code cannot use it, because they do not have the verifier \cite[sec.~1]{ietf-rfc7636-pkce}. If it matches, Keycloak returns an access token and a refresh token. The access token is a JWT that is valid for 15 minutes and names our API as its audience.

\paragraph{6. Call the API.} The client sends the token in the Authorization header as a bearer token \cite[sec.~2.1]{ietf-rfc6750-bearer}.

\paragraph{7. Get Keycloak's keys.} The first time, the API fetches Keycloak's public signing keys and keeps them. After that it only fetches them again when it sees a key it does not know, or after a long time.

\paragraph{8. Check the token and answer.} The API checks the token on its own: the signature, who issued it, that it is meant for our API, and that it has not expired \cite{ietf-rfc7519-jwt}. It then reads the user's roles from the token. A missing or invalid token gives 401. So does a valid token without a user id, because the API cannot tell who the user is. A valid token without the admin role gives 403 on admin endpoints.

So the password only travels between the user and Keycloak, and the API only ever sees the token. This is what the supervisor asked us to show at the meeting on 6/10.

\subsection{Customer App and Admin Panel}
The two clients follow the same eight steps, each with its own client in Keycloak. The customer app is sent back to the app through the app's own address scheme, which the phone opens in the app. The admin panel is sent back to its web address, and the browser calls the token endpoint from JavaScript, so Keycloak must allow the admin panel's origin.

Both clients renew the access token in the background with a refresh token, so the user does not have to log in again when the token runs out after 15 minutes. The customer app also keeps the refresh token on the phone, so the user stays logged in when the app is restarted (appendix 4.1). This only works as long as the user's session in Keycloak is alive. The session ends after 30 minutes without use, and never lasts longer than 10 hours. We do not ask for offline access, so after that the user has to log in again.

The app's address scheme is just the word prepmeup. The standard for native apps says the scheme should be a reversed domain name that we own \cite[sec.~7.1]{ietf-rfc8252-native-apps}. With a plain word, another app could register the same scheme and receive the code. PKCE stops that app from using the code \cite[sec.~8.1]{ietf-rfc8252-native-apps}, but we should still change the scheme.

We checked the first half of the flow in the browser against the local stack. The request to the login page asked for a code with an S256 challenge, and the redirect back carried the code and the state. The token request and the API call in the figure are drawn from the client code and the API's setup, and have not been checked in the browser's developer tools yet. For the admin panel we have also seen the end of the flow in the API's log, when the panel ran as a container on the local stack. An admin got 200 on the admin ping, and a customer got 403.

\section{Token Validation}
The browser and the phone reach Keycloak on a public address, but the API reaches it on an internal address inside the Docker network. In the local setup these are port 8082 on localhost and the service name keycloak on port 8080. The token says it was issued by the public address, so the API is configured with two addresses. The first is the public address, which must match the issuer in the token. The second is the internal address, where the API fetches Keycloak's configuration and signing keys.

Keycloak is set up in the local stack so that its configuration points to the internal address for the keys. The internal address uses plain HTTP, because it is only reached inside the Docker network. The API is therefore told that HTTP is allowed for this fetch. The same setting is used in production.

The API only turns on token checking when an address for Keycloak is configured. Without it, the API has no way to validate tokens.
