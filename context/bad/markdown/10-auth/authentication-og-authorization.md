# Authentication & Authorisation in ASP.NET Core WebAPI

## Definitions

- **Authentication** is the process of verifying that "you are who you say you are".
- **Authorization** is the process of verifying that "you are permitted to do what you are trying to do".

## The HTTP protocol is stateless

If each request doesn't know what happened before it, how can we know whether the user has been authenticated?

## How to authorize a stateless call?

- **Cookies** — a sessionId is sent to the browser via a cookie so it is resent on all subsequent requests and used on the server to retrieve the user's session and act accordingly.
- **Bearer tokens** — an encrypted token generated by the authentication server containing the relevant authorization info. The token is sent to the client, which uses it for subsequent requests by setting it in the `Authorization` HTTP header.
- **API keys** — the service operating the web API gives its users a ClientID used to access the API.
- **Signatures and certificates** — perform a hash of the request using a previously shared private key and/or a Transport Layer Security (TLS) certificate.

## What are cookies?

- Cookies are pieces of data, normally stored in text files, that websites place on visitors' computers to store information, usually specific to that visitor.
- Cookies allow you to log in on one page, move around to other pages and stay logged in, and let preferences be remembered.
- Cookies can also be used to track pages you visit between sites, letting advertisers build a picture of your interests ("behavioural advertising").
- Incredibly useful, but can also manipulate your web experience in unexpected or unwanted ways.

## EU legislation on cookies

- The ePrivacy directive — specifically Article 5(3) — requires prior informed consent for storage of or access to information stored on a user's terminal equipment. In other words, you must ask users if they agree to most cookies and similar technologies.
- Consent is **not** required for:
  - user-input cookies (session-id), e.g. first-party cookies tracking user input in forms and shopping carts, for a session (or persistent cookies limited to a few hours in some cases)
  - authentication cookies, to identify the user once logged in, for the duration of a session
  - user-centric security cookies, used to detect authentication abuses, for a limited persistent duration
  - multimedia content player cookies (technical data for audio/video playback), for the duration of a session
  - load-balancing cookies, for the duration of a session
  - user-interface customisation cookies (language, font preferences), for a session or slightly longer
  - third-party social plug-in content-sharing cookies, for logged-in members of a social network

## The different types of cookies

- By **lifespan**:
  - session cookie — erased when the user closes the browser
  - persistent cookie — remains on the user's device for a pre-defined period
- By **domain**:
  - first-party cookies — set by the web server of the visited page, same domain
  - third-party cookies — stored by a different domain than the visited page's domain

## Cookie limitations

- Cookies are sent with every request, so their size should be kept to a minimum — ideally only an identifier, with actual data stored on the server.
- Most browsers restrict cookies to 4096 bytes; only a limited number of cookies is available per domain.
- Users can clear their cookies at any time, wiping out stored settings regardless of expiration.
- The browser automatically sending cookies has a big downside: **CSRF attacks** — a malicious website exploits the fact that the browser automatically attaches authentication cookies to requests to a domain, and tricks the browser into executing a request.

## Bearer tokens

- Offer a decent security posture and are easy to implement.
- JWT is **self-contained**:
  - The server can validate the token and use its claims without fetching corresponding information from a store.
  - It is digitally signed, so any modification is detected by the server.
  - Suitable for microservices architectures and native apps.

### Authentication flow

Login → the authentication server issues a signed token → the client stores it and sends it on subsequent requests. **No data is stored by the server.**

### Bearer token drawbacks

- After tokens are issued, they can't be invalidated (or updated) easily.
- If a third party steals a token, they can perform authorized requests until the token expires — and neither developers, sysadmins nor users can easily revoke it, even knowing it's compromised.
- Best workaround: reduce the token lifespan as much as possible (ideally a few minutes) so an attacker has little time to act. A **refresh token** can then be used to keep good UX.

## What is ASP.NET Core Identity?

- Identity is a membership system which adds login functionality to your application.
- Users can create an account and log in with username/password, or use external login providers such as Facebook, Google, Microsoft Account, Twitter and more.
- Identity can use a SQL Server database to store usernames, passwords and profile data — or your own persistent store, e.g. Azure Table Storage or MongoDB.
- By default, Identity uses cookies for authentication, but it can be configured to use bearer tokens (JWT).

## To use ASP.NET Core Identity

1. Install the required NuGet packages
2. Create a new user entity class to handle user data such as username and password
3. Update the existing `ApplicationDbContext` to deal with the new user entity
4. Add and apply a new migration to create the database tables required by Identity
5. Set up and configure the required identity services and middleware in `Program.cs`
6. Implement a new controller to handle registration (create a new user) and login (create temporary access tokens for an authenticated user)

### Install the NuGet packages

- `Microsoft.Extensions.Identity.Core` — the membership system and the main classes and services for the login features
- `Microsoft.AspNetCore.Identity.EntityFrameworkCore` — the ASP.NET Core Identity provider for EF Core
- `Microsoft.AspNetCore.Authentication.JwtBearer` — middleware enabling ASP.NET Core applications to handle JSON Web Tokens

### Create the user entity

Name the entity `ApiUser` (or `AppUser`) — calling it `User` would conflict with built-in properties such as `ControllerBase.User`. Extend the framework's default `IdentityUser`:

```csharp
using Microsoft.AspNetCore.Identity;

namespace MyBGList_Chap9.Models
{
    public class ApiUser : IdentityUser
    {
        [MaxLength(100)]
        public string? FullName { get; set; }
    }
}
```

### Update the ApplicationDbContext

Change the base class from `DbContext` to `IdentityDbContext<ApiUser>` to include the Identity functionality:

```csharp
using Microsoft.AspNetCore.Identity.EntityFrameworkCore;

namespace MyBGList_Chap6.Data
{
    public class ApplicationDbContext : IdentityDbContext<ApiUser>
    {
        public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
            : base(options)
        {
        }
    }
}
```

### Add and apply a new migration


## Setting up the services and middleware

In `Program.cs` we need to add:

- **The identity service** — to perform the registration and login processes
- **The authorization service** — to define the rules for issuing and reading JWTs
- **The authentication middleware** — to add the JWT reading task to the HTTP pipeline

### Add the identity service

Add the Identity service to the service container and configure the minimum security requirements for user passwords:

```csharp
using Microsoft.AspNetCore.Identity;

builder.Services.AddIdentity<ApiUser, IdentityRole>(options =>
{
    options.Password.RequireDigit = true;
    options.Password.RequireLowercase = true;
    options.Password.RequireUppercase = true;
    options.Password.RequireNonAlphanumeric = true;
    options.Password.RequiredLength = 8;
})
.AddEntityFrameworkStores<ApplicationDbContext>();
```

### Add the authentication service

Define JWT as the default authentication method, enable the JWT bearer authentication handler, and configure JWT validation:

```csharp
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.IdentityModel.Tokens;

builder.Services.AddAuthentication(options => {
    options.DefaultAuthenticateScheme =
    options.DefaultChallengeScheme =
    options.DefaultForbidScheme =
    options.DefaultScheme =
    options.DefaultSignInScheme =
    options.DefaultSignOutScheme = JwtBearerDefaults.AuthenticationScheme;
}).AddJwtBearer(options => {
    options.TokenValidationParameters = new TokenValidationParameters
    {
        ValidateIssuer = true,
        ValidIssuer = builder.Configuration["JWT:Issuer"],
        ValidateAudience = true,
        ValidAudience = builder.Configuration["JWT:Audience"],
        ValidateIssuerSigningKey = true,
        IssuerSigningKey = new SymmetricSecurityKey(
            System.Text.Encoding.UTF8.GetBytes(
                builder.Configuration["JWT:SigningKey"]))
    };
});
```

### Update appsettings.json

Add a top-level section (below the existing SeriLog key):

```json
"JWT": {
    "Issuer": "MyBGList",
    "Audience": "MyBGList",
    "SigningKey": "MyVeryOwnTestSigningKey123$"
}
```

Moving the SigningKey to `secrets.json` gives a better security posture — do that in real projects.

### Add the authentication middleware

Add the authentication middleware immediately **before** `app.UseAuthorization()`:

```csharp
app.UseAuthentication();
app.UseAuthorization();
```

## Implement the AccountController

Create a new `AccountController` with two action methods:

- **Register** — to create new users
- **Login** — to authenticate them

It needs the services `UserManager` (APIs for managing users) and `SignInManager` (APIs for logging users in), both from `Microsoft.AspNetCore.Identity`:

```csharp
public class AccountController : ControllerBase
{
    private readonly ApplicationDbContext _context;
    private readonly ILogger<DomainsController> _logger;
    private readonly IConfiguration _configuration;
    private readonly UserManager<ApiUser> _userManager;
    private readonly SignInManager<ApiUser> _signInManager;

    public AccountController(
        ApplicationDbContext context,
        ILogger<DomainsController> logger,
        IConfiguration configuration,
        UserManager<ApiUser> userManager,
        SignInManager<ApiUser> signInManager)
    {
        _context = context;
        _logger = logger;
        _configuration = configuration;
        _userManager = userManager;
        _signInManager = signInManager;
    }
}
```

### RegisterDTO class

The DTO that transports the data for user registration (sign-up):

```csharp
public class RegisterDTO
{
    [Required]
    public string? FullName { get; set; }
    [Required]
    [EmailAddress]
    public string? Email { get; set; }
    [Required]
    public string? Password { get; set; }
}
```

### Register method

```csharp
public async Task<ActionResult> Register(RegisterDTO input)
{
    try
    {
        if (ModelState.IsValid)
        {
            var newUser = new ApiUser();
            newUser.UserName = input.Email;
            newUser.Email = input.Email;
            newUser.FullName = input.FullName;
            var result = await _userManager.CreateAsync(newUser, input.Password);
            if (result.Succeeded)
            {
                _logger.LogInformation(
                    "User {userName} ({email}) has been created.",
                    newUser.UserName, newUser.Email);
                return StatusCode(201,
                    $"User '{newUser.UserName}' has been created.");
            }
            else
                throw new Exception(
                    string.Format("Error: {0}", string.Join(" ",
                    result.Errors.Select(e => e.Description))));
        }
        // else ... (validation error handling)
    }
    // catch ...
}
```

### Never save a password

- You must **never store a password** in plain text.
- `UserManager.CreateAsync` will salt and hash the password to a non-reversible hash value and salt, stored in the `[AspNetUsers].[PasswordHash]` column.

### Login method

```csharp
public async Task<ActionResult> Login(LoginDTO input)
{
    try
    {
        if (ModelState.IsValid)
        {
            var user = await _userManager.FindByNameAsync(input.UserName);
            if (user == null || !await _userManager.CheckPasswordAsync(user, input.Password))
                throw new Exception("Invalid login attempt.");
            else
            {
                var signingCredentials = new SigningCredentials(
                    new SymmetricSecurityKey(
                        System.Text.Encoding.UTF8.GetBytes(_configuration["JWT:SigningKey"])),
                    SecurityAlgorithms.HmacSha256);
                var claims = new List<Claim>();
                claims.Add(new Claim(ClaimTypes.Name, user.UserName));
                var jwtObject = new JwtSecurityToken(
                    issuer: _configuration["JWT:Issuer"],
                    audience: _configuration["JWT:Audience"],
                    claims: claims,
                    expires: DateTime.Now.AddSeconds(300),
                    signingCredentials: signingCredentials);
                var jwtString = new JwtSecurityTokenHandler().WriteToken(jwtObject);
                return StatusCode(StatusCodes.Status200OK, jwtString);
            }
        }
        // else ...
    }
    // catch ...
}
```

## Authorization — server-side and client-side

- **Server-side** — set up authorization rules to make some of the existing controller (and Minimal API) action methods accessible only to callers with a valid JWT containing the required claims.
- **Client-side** — add an `Authorization` HTTP header containing the JWT to emulate "authorized" requests with the test client of choice (SwaggerUI or Postman).

### Adding authorization to Scalar (OpenAPI)

```csharp
builder.Services.AddOpenApi(options =>
{
    options.AddDocumentTransformer((document, context, cancellationToken) =>
    {
        document.Components ??= new();
        document.Components.SecuritySchemes ??= new Dictionary<string, IOpenApiSecurityScheme>();
        document.Components.SecuritySchemes.Add("Bearer", new OpenApiSecurityScheme
        {
            In = ParameterLocation.Header,
            Description = "Please enter token",
            Name = "Authorization",
            Type = SecuritySchemeType.Http,
            BearerFormat = "JWT",
            Scheme = "bearer"
        });
        return Task.CompletedTask;
    });
});
```

## The [Authorize] attribute

- Choose which API endpoints should be available to everyone and which to restrict.
- Typical approach: allow public/anonymous access to read-only endpoints that don't disclose reserved data, and restrict everything else to authenticated (and authorized) users.
- Restrict access to endpoints by decorating them with `[Authorize]`:

```csharp
[Authorize]
[HttpPost(Name = "UpdateBoardGame")]
[ResponseCache(NoStore = true)]
public async Task<RestDTO<BoardGame?>> Post(BoardGameDTO model)
{
    // ...
}
```

### Choosing the default access behavior

You can reverse the logic to default-block/opt-allow by putting `[Authorize]` on the whole controller and selectively using `[AllowAnonymous]` on the action methods that should be public:

```csharp
[Authorize]
[Route("[controller]")]
[ApiController]
public class MechanicsController : ControllerBase
{
    [AllowAnonymous]
    [HttpGet(Name = "GetMechanics")]
    [ResponseCache(Location = ResponseCacheLocation.Any, Duration = 60)]
    public async Task<RestDTO<Mechanic[]>> Get(
        [FromQuery] RequestDTO<MechanicDTO> input)
    {
        // ...
    }
}
```

- It can also be set globally in Program.cs: `GlobalFilters.Filters.Add(new AuthorizeAttribute())`.
- If you set it globally or on all controllers, you must open up anonymous access to the register and login actions, otherwise no one can log in:

```csharp
[Authorize]
public class AccountController : ControllerBase
{
    [AllowAnonymous]
    [HttpPost]
    public async Task<ActionResult> Register(RegisterDTO input)
    {
        // ...
    }
}
```

## The principal is the current user

The `HttpContext` object exposes the current principal for a request as the `User` property. The authentication middleware deserializes the `ClaimsPrincipal` from the encrypted cookie or JWT before the authorize filter runs.

## RBAC and claims-based authorization

- **Role-based access control (RBAC)**:
  - Users are assigned one or more roles.
  - You configure which role(s) are allowed to access which resources (actions and/or data).
- **Claims-based authorization**:
  - Users are assigned one or more claims.
  - You configure which claim gives access to a restricted resource (action or data).
  - You may still use roles to associate claims with users — or use claims to associate a role with a user.

### Claims

- A claim is a piece of information about a user consisting of a **type** and an optional **value**.
- You prove who you are (authentication) in order to retrieve the claims you need for authorization.
- Authorization protects sensitive actions and information.

### Using roles

Append `AddRoles` to add role services:

```csharp
public void ConfigureServices(IServiceCollection services)
{
    services.AddDbContext<ApplicationDbContext>(options =>
        options.UseSqlServer(Configuration.GetConnectionString("DefaultConnection")));
    services.AddDefaultIdentity<ApiUser>()
        .AddRoles<IdentityRole>()
        .AddEntityFrameworkStores<ApplicationDbContext>();
}
```

### Seeding an admin user

```csharp
public static void SeedUsers(UserManager<ApiUser> userManager)
{
    const string adminEmail = "Admin@localhost";
    const string adminPassword = "Secret7$";
    if (userManager == null)
        throw new ArgumentNullException(nameof(userManager));
    if (userManager.FindByNameAsync(adminEmail).Result == null)
    {
        var user = new ApiUser();
        user.UserName = adminEmail;
        user.Email = adminEmail;
        user.EmailConfirmed = true;
        IdentityResult result = userManager.CreateAsync(user, adminPassword).Result;
        if (result.Succeeded)
        {
            var adminUser = userManager.FindByNameAsync(adminEmail).Result;
            var claim = new Claim("IsAdmin", "true");
            var claimAdded = userManager.AddClaimAsync(adminUser, claim).Result;
        }
    }
}
```

Call `SeedData.SeedUsers` from `Program.cs`:

```csharp
app.UseAuthentication();
app.UseAuthorization();

using (var scope = app.Services.CreateScope())
{
    var serviceProvider = scope.ServiceProvider;
    var userManager = serviceProvider.GetService<UserManager<ApiUser>>();
    if (userManager != null)
        SeedData.SeedUsers(userManager);
    else throw new Exception("Unable to get UserManager!");
}

app.Run();
```

## Handling unauthorized requests

If the requirements are not met, the authorization filter short-circuits the request and returns one of two `IActionResult` types:

- **ChallengeResult** — the user was not authorized because they haven't logged in yet.
- **ForbidResult** — the user was logged in but didn't meet the requirements (missing a required claim or role).

## Claims-based access control (CBAC)

- Gives more granular control than RBAC.
- Claims requirements are policy-based, so they must be explicitly declared by defining and registering a policy in `Program.cs`.

### How to add policies

Add policies by calling `AddPolicy()` on the `AuthorizationOptions` object. `RequireClaim(type, values)` checks for a claim with a given value; `RequireClaim(type)` checks only for the presence of a claim:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("ModeratorWithMobilePhone",
        policy => policy
            .RequireClaim(ClaimTypes.Role, RoleNames.Moderator)
            .RequireClaim(ClaimTypes.MobilePhone)
    );
    options.AddPolicy("SomeOtherPolicy",
        /* ... */);
});
```

### How to require a policy

The policy name given in `AddPolicy` must match the value used in the `[Authorize]` attribute:

```csharp
[Authorize(Policy = "ModeratorWithMobilePhone")]
```

### AuthorizationPolicyBuilder methods

| Method | Policy behavior |
|---|---|
| `RequireAuthenticatedUser()` | The user must be authenticated. Similar to the default `[Authorize]` attribute without a policy. |
| `RequireClaim(claim, values)` | The user must have the specified claim, optionally with one of the specified values. |
| `RequireUsername(username)` | The user must have the specified username. |
| `RequireAssertion(function)` | Executes the provided lambda, returning a bool indicating whether the policy was satisfied. |
| `RequireRole()` | Role-based authorization; possible in ASP.NET Core but primarily for legacy compatibility. |

## Policy-based access control (PBAC)

- For complex checks, use policy-based access control.
- Similar to CBAC, but instead of checking for the presence (and optionally values) of claims, it uses a more generic interface composed of one or more **requirements** (`IAuthorizationRequirement`) and **requirement handlers** (`IAuthorizationHandler`).
- Both RBAC and CBAC can be seen as simplified implementations of PBAC based on preconfigured policies.

### Simple "equal to or greater than 18" policy

```csharp
options.AddPolicy("MinAge18", policy =>
    policy
        .RequireAssertion(ctx =>
            ctx.User.HasClaim(c => c.Type == ClaimTypes.DateOfBirth)
            && DateTime.ParseExact("yyyyMMdd",
                ctx.User.Claims.First(c =>
                    c.Type == ClaimTypes.DateOfBirth).Value,
                System.Globalization.CultureInfo.InvariantCulture)
                >= DateTime.Now.AddYears(-18)));
```

### Creating custom policies for authorization

- A custom policy can have many requirements, and every requirement can have many handlers.
- For a policy to be satisfied, a user must fulfil **all** requirements.
- But not all handlers for a requirement need to be satisfied — one is enough.

Policy with multiple requirements:

```csharp
options.AddPolicy("CanAccessLounge", policyBuilder =>
    policyBuilder.AddRequirements(
        new MinimumAgeRequirement(18),
        new AllowedInLoungeRequirement()
    ));
```

### Requirements

Authorization requirements are any class implementing the `IAuthorizationRequirement` interface — a blank marker interface:

```csharp
public class AllowedInLoungeRequirement : IAuthorizationRequirement { }
```

By providing the minimum age as a constructor parameter, the requirement can be reused in other policies with different minimum ages:

```csharp
public class MinimumAgeRequirement : IAuthorizationRequirement
{
    public MinimumAgeRequirement(int minimumAge)
    {
        MinimumAge = minimumAge;
    }
    public int MinimumAge { get; }
}
```

### Authorization handlers

- Handlers contain the logic of how a specific `IAuthorizationRequirement` can be satisfied.
- When executed, a handler can do one of three things:
  - Mark the requirement handling as a success
  - Not do anything
  - Explicitly fail the requirement
- Handlers implement `AuthorizationHandler<T>`, where T is the type of requirement they handle.

```csharp
public class FrequentFlyerHandler :
    AuthorizationHandler<AllowedInLoungeRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        AllowedInLoungeRequirement requirement)
    {
        var hasClaim =
            context.User.HasClaim(Claims.FrequentFlyerClass, "Gold");
        if (hasClaim)
        {
            context.Succeed(requirement);
        }
        return Task.CompletedTask;
    }
}
```

### Registering the authorization handlers with the DI container

```csharp
public void ConfigureServices(IServiceCollection services)
{
    // ...
    services.AddSingleton<IAuthorizationHandler, MinimumAgeHandler>();
    services.AddSingleton<IAuthorizationHandler, FrequentFlyerHandler>();
    services.AddSingleton<IAuthorizationHandler, BannedFromLoungeHandler>();
    services.AddSingleton<IAuthorizationHandler, IsAirlineEmployeeHandler>();
}
```

If handlers have scoped or transient dependencies (e.g. the EF Core DbContext), register them as scoped instead.

## Resource-based authorization (imperative authorization)

ASP.NET Core exposes `IAuthorizationService`, which can be injected into controllers for imperative authorization:

```csharp
public RecipeController(RecipeService service,
                        UserManager<ApplicationUser> userService,
                        IAuthorizationService authService)
{
    _service = service;
    _userService = userService;
    _authService = authService;
}

[Authorize]
public async Task<IActionResult> Edit(int id)
{
    var recipe = _service.GetRecipe(id);
    var authResult = await _authService.AuthorizeAsync(User, recipe, "CanManageRecipe");
    if (!authResult.Succeeded)
    {
        return new ForbidResult();
    }
    var model = _service.GetRecipeForUpdate(id);
    if (model == null)
    {
        return NotFound();
    }
    return View(model);
}
```

### The steps

Define the "CanManageRecipe" policy — same process as declarative authorization:

- Create a policy in `ConfigureServices` by calling `AddAuthorization()`
- Define one or more requirements for the policy
- Define one or more handlers for each requirement
- Register the handlers in the DI container

Requirement and policy:

```csharp
public class IsRecipeOwnerRequirement : IAuthorizationRequirement { }

public void ConfigureServices(IServiceCollection services)
{
    services.AddAuthorization(options => {
        options.AddPolicy("CanManageRecipe", policyBuilder =>
            policyBuilder.AddRequirements(new IsRecipeOwnerRequirement()));
    });
}
```

Handler implementation — note the extra generic parameter for the resource type (`Recipe`):

```csharp
public class IsRecipeOwnerHandler : AuthorizationHandler<IsRecipeOwnerRequirement, Recipe>
{
    private readonly UserManager<IdentityUser> _userManager;

    public IsRecipeOwnerHandler(UserManager<IdentityUser> userManager)
    {
        _userManager = userManager;
    }

    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        IsRecipeOwnerRequirement requirement,
        Recipe resource)
    {
        var appUser = await _userManager.GetUserAsync(context.User);
        if (appUser == null)
        {
            return;
        }
        if (resource.CreatedById == appUser.Id)
        {
            context.Succeed(requirement);
        }
    }
}
```

Add the handler to the DI container:

```csharp
services.AddScoped<IAuthorizationHandler, IsRecipeOwnerHandler>();
```

## Authorization servers (Identity Servers)

### Authorization and microservice architecture

- Someone tries to access a secure part of your site.
- They are not currently known to your app (not logged in), so your app redirects them to your chosen authority (authorization server), which prompts them to identify themselves — usually username/password.
- Once the authorization server is satisfied that the user is who they claim to be, it issues a token and redirects them back to your app.
- Your app stores the identity information (typically passed to and from the browser via a secure cookie or a JWT).
- When asked to serve a restricted resource, your app checks the authorization token and grants access if the token is legitimate and entitles the user to the resource.

### OAuth2 specification

- An open standard for authorization.
- Specifies a process for resource owners to authorize third-party access to their server resources **without sharing their credentials**.
- Focuses on client developer simplicity while providing specific authorization flows for web applications, desktop applications, mobile phones and living-room devices.
- Developed within the IETF OAuth WG; published as RFC 6749 in October 2012.
- Commonly used to let users log into third-party websites with their Microsoft, Google, Facebook or Twitter accounts without exposing their password.

### Authorization server options

- IdentityServer 4
- Azure Active Directory
- Auth0
- OpenIddict
- Stormpath
- Google OAuth 2.0
- Facebook Login
- Keycloak
- Etc.
