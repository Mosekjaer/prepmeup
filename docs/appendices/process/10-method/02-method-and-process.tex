\subsection*{2/9}
\begin{itemize}
    \item We went with user stories to try something other than fully dressed use cases. User stories appealed to the team, because they are written in the customer's own words, as close to the consumer as possible. That made it easier to validate the requirements and keep the focus on delivering what the consumer wants.
    \item In the requirements specification, a lot of thought went into the database: which relations there should be between the ``members'' of the database.
    \item We created user stories before sprint 1 began. We followed the setup from Brightspace.
    \item During the requirements specification the group spent a lot of time discussing the scope of the project and how the database should be built. Should every customer be able to swap a single food item, or should there be a fixed number of packages whose content cannot be replaced? We chose packages with fixed content, because we assumed that most customers would pick a ``standard package'', a ``vegetarian package'' or a ``gluten-free package''. One package covers the whole household. One package per person would probably also work, but we made it a ``Could'' in MoSCoW, because we saw it as a small change to the system.
    \item Concept clarification started.
\end{itemize}

\subsection*{9/9}
\begin{itemize}
    \item Fred presented how the project could be shaped with AI as a development tool. Everyone agreed. The slides are in the architecture pitch.
    \item We also dropped Notion and chose Kaneo. Kaneo is an open-source alternative to Trello. It is easy to use and has what we need, without the information overload of larger tools such as Jira. It also works with Claude, so Claude would be able to create and pick tickets and complete them.
\end{itemize}

\subsection*{15/9}
\begin{itemize}
    \item Review \#1 with group 4. Their feedback led to FR/NFR numbering and testable NFRs in the requirements specification.
    \item We agreed that step 2 is to add an external authority for login, and discussed Firebase, Keycloak, Clerk and OAuth.
    \item We agreed on one shared deployment instead of everyone running the system locally, because an administrator needs to work on the same data as the customers.
\end{itemize}

\subsection*{16/9}
\begin{itemize}
    \item The project skeleton was set up: the layered .NET solution, test projects, the Expo app, the React admin panel and the shared api-client in one npm workspace.
    \item Keycloak was chosen as identity provider and runs in docker compose. Coolify on our own server was chosen for deployment. The reasons are in appendix 2.1.
    \item We use GitHub instead of GitLab, which the first architecture pitch planned for. GitHub Actions builds and tests on every pull request.
    \item We chose GitHub Flow with Conventional Commits and named branches. Git hooks and a GitHub Actions check make sure the rules are followed. See appendix 10.1.
    \item We changed our mind about Claude and Kaneo: the AI may read, comment on and create tasks, but moving, assigning and deleting tasks is done by the group. Planning the sprint is part of what we have to learn ourselves.
    \item We decided that all text in the apps is in English.
\end{itemize}

\subsection*{23/9}
\begin{itemize}
    \item Sprints are two weeks, from Wednesday to Tuesday. Sprint 1 runs from 16/9 to 29/9. The sprint calendar is in appendix 10.1.
    \item The Backlog view in Kaneo is our product backlog, and the board is the sprint backlog.
    \item Tasks get labels for story points, sprint and epic, so we can measure velocity and trace a task back to the requirements.
\end{itemize}

\subsection*{30/9}
\begin{itemize}
    \item Sprint 2 was shortened to a one-week mini sprint, so the unfinished work from sprint 1 can be shown in a demo at the sprint review on 7/10. Sprints 3 to 6 moved one week earlier.
    \item Every sprint ends with a demo, so everyone knows the parts they did not work on themselves.
    \item Tasks in the backlog have no sprint label. The label is added when a task is pulled into a sprint.
\end{itemize}

\subsection*{6/10}
\begin{itemize}
    \item We changed the rule for Claude and Kaneo again. Claude may now move tasks between the backlog and the board when a group member asks. Which tasks are moved, and when, is still decided by the group.
\end{itemize}

\subsection*{7/10}
\begin{itemize}
    \item Sprint 3 was extended by one week to 27/10, because the autumn break falls in the middle of it. Sprints 4 to 6 moved one week later, so sprint 6 ends on 8/12.
    \item Claude may now estimate a task and set its story point label when a group member asks. The group corrects the estimate if it disagrees.
\end{itemize}

\section*{Velocity}
Committed is the sum of story points in \emph{To Do} at sprint planning. Done is the sum in \emph{Done} at sprint review. Spillover is the points that move on to the next sprint. Backlog size is the sum of all estimated points in the project at sprint review.

The numbers are kept in one CSV file in the docs folder. The table below and the burn-up chart in chapter~2 of the report are both generated from that file, so it is the only place the numbers are entered.
