\section{Overview}
PrepMeUp runs as a set of Docker containers started with docker compose. There are two setups, each with its own compose file: one for local development and one for production on our server with Coolify. In both, all containers are on the same Docker network and find each other by service name, for example db and keycloak. Why we chose Keycloak and Coolify is described in appendix 2.1.

The two clients are not containers in compose. The customer app runs on the phone, and the admin panel runs in the browser. Both talk to the API over HTTP(S), and both send the user to Keycloak to log in.

The database has no host port, so only the API can reach it. The API waits until the database health check passes before it starts. Keycloak imports our realm file at startup. The admin panel (Vite, port 5173) and the Expo app (port 8081) run outside Docker, and the API's CORS policy allows these two addresses. The data from the database and Keycloak is kept in two Docker volumes.

\subsection{Token Validation}
The browser and the phone reach Keycloak on port 8082 on localhost, but inside Docker the API reaches it by its service name on port 8080. The token says it was issued by the localhost address, so the API is configured with two addresses. The first is the public address, which must match the issuer in the token. The second is the internal address, where the API fetches Keycloak's configuration and signing keys.

\section{Production}

\begin{center}
\begin{tabular}{@{}l l p{7cm}@{}}
\textbf{Service} & \textbf{Image} & \textbf{Purpose} \\
\hline
api & built from the Api project & ASP.NET Core Web API \\
db & SQL Server 2022 & Application data \\
keycloak & Keycloak 26.3 & Login and roles, runs in production mode \\
keycloak-db & PostgreSQL 17 & Keycloak's own data (users, sessions) \\
\end{tabular}
\end{center}

No container publishes a port. Coolify's reverse proxy receives the traffic from the internet on HTTPS and forwards it to the API and Keycloak on port 8080 inside the network. Because HTTPS ends at the proxy, Keycloak reads the forwarded headers to know the original address and scheme. The two databases can only be reached from inside the network.

The public URLs of the admin panel, the customer app and Keycloak are set as environment variables in Coolify. The same variables are used for the API's CORS policy and the redirect addresses in the Keycloak realm. All services are set to restart, so they start again after a crash or a server restart.

\section{Login Flow}
Both clients use the Authorization Code flow with PKCE:
\begin{enumerate}
    \item The client opens Keycloak's login page in the browser.
    \item The user logs in at Keycloak. The password is never sent to the client or the API.
    \item Keycloak redirects back to the client with a short-lived code. For the app, the redirect uses the app's own URL scheme.
    \item The client exchanges the code for an access token (a JWT, valid for 15 minutes).
    \item The client sends the token to the API in the Authorization header.
    \item The API checks the token's signature, issuer and audience, and uses the role (household or admin) for authorization.
\end{enumerate}

Keycloak already adds our API as audience to the tokens for both clients. Step 6 is not implemented in the API yet.
