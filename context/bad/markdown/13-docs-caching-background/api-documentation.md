# SW4BAD: API Documentation

Contents: API Documentation, Best Practices, XML and Swashbuckle.

## API documentation

- An API is a software platform that exposes tools and services; its purpose is to create a specification for "third-party" developers
- Documentation is not an option: it is a requirement (as long as you want to increase or speed adoption)
- Developer eXperience (DX)
- A means of communication amongst all the parties involved

## Web API potential audience

Using names from construction slang:

- **Prospectors** — passionate developers and IT enthusiasts willing to give the web API a try without a compelling need beyond personal interest, knowledge gaining, testing/reviewing purposes, etc.
- **Contractors** — the IT analysts, solution architects and backend designers who take responsibility for creating products, solving problems, or addressing challenges the web API could help with. They typically don't get down to implementation, but often serve as decision-makers
- **Builders (third-party developers)** — the software developers who choose (or are instructed) to use the web API to solve a specific problem. The most technical part of the audience and can be difficult to satisfy

## Best practices

- **Adopting an automated description tool** — so the documentation won't become stale or outdated if we forget to update it along with the web API's source code
- **Describing endpoints and input parameters** — so the audience not only acknowledges their existence, but also learns their purposes and how to use them
- **Describing responses** — so the audience knows what to expect when calling each endpoint and how to handle the outcome
- **Adding request and response samples** — saves the audience a huge amount of development time
- **Grouping endpoints into sections** — to better separate users' different scopes, purposes, and roles
- **Excluding reserved endpoints** — to prevent users from being aware of their existence and/or trying to call them
- **Emphasizing authorization requirements** — to let the audience distinguish between publicly accessible operations and those restricted to authorized users
- **Customizing the documentation context** — choosing appropriate names, icons and metadata to help users find the required info

## Adopt an automated tool

- To satisfy a third-party developer, the API documentation must always be updated — otherwise users will perceive the API as broken
- True even for internal APIs used only by internal developers: lack of proper documentation eventually affects new employees, potential partners, maintenance tasks, handover processes, outsourcers, etc.
- The need to automate documentation is particularly strong for RESTful APIs, because the REST architectural standard doesn't provide a standardized mechanism, schema, or reference for that purpose
- This is the main reason behind the success of OpenAPI (Swagger):
  - Code generates `swagger.json` and SwaggerUI for endpoint testing
  - Details can be added to it

## Describe endpoints and input parameters

The SwaggerUI main dashboard by default consists merely of a list of endpoints and their input variables, without descriptions. Swashbuckle provides two ways to add custom descriptions:

1. Use an XML documentation file autogenerated by the .NET compiler from standard triple-slash, XML-formatted comments in the C# classes
2. Use the `[SwaggerOperation]` data attribute, provided by the optional `Swashbuckle.AspNetCore.Annotations` NuGet package

## Working with XML

1. Annotate (just type `///`):

```csharp
/// <summary>
/// Registers a new user.
/// </summary>
/// <param name="input">A DTO containing the user data.</param>
/// <returns>A 201 - Created Status Code in case of success.</returns>
[HttpPost]
[ResponseCache(CacheProfileName = "NoCache")]
public async Task<ActionResult> Register(RegisterDTO input)
```

2. Update the project configuration file (`MyBGList.csproj`) to generate documentation files:

```xml
<PropertyGroup>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
  <NoWarn>$(NoWarn);1591</NoWarn>
</PropertyGroup>
```

3. Configure Swashbuckle to read the documentation files (`Program.cs`):

```csharp
using System.Reflection;  // Required namespace

builder.Services.AddSwaggerGen(options =>
{
    var xmlFilename =
        $"{Assembly.GetExecutingAssembly().GetName().Name}.xml";   // Builds the XML documentation filename
    options.IncludeXmlComments(System.IO.Path.Combine(
        AppContext.BaseDirectory, xmlFilename));                   // Assembles the XML documentation file full path
});
```

The `<summary>` and `<param>` texts then show up in SwaggerUI next to the endpoints.

## Working with Swashbuckle annotations

1. Install the NuGet package:

```bash
dotnet add package Swashbuckle.AspNetCore.Annotations --version 6.4.0
```

2. Use the `SwaggerOperation` attribute:

```csharp
using Swashbuckle.AspNetCore.Annotations;  // Required namespace

[HttpGet(Name = "GetBoardGames")]
[ResponseCache(CacheProfileName = "Any-60")]
[SwaggerOperation(
    Summary = "Get a list of board games.",
    Description = "Retrieves a list of board games " +
        "with custom paging, sorting, and filtering rules.")]
public async Task<RestDTO<BoardGame[]>> Get( /* ... */ )

[HttpGet("{id}")]
[ResponseCache(CacheProfileName = "Any-60")]
[SwaggerOperation(
    Summary = "Get a single board game.",
    Description = "Retrieves a single board game with the given Id.")]
public async Task<RestDTO<BoardGame?>> Get(int id)

[Authorize(Roles = RoleNames.Moderator)]
[HttpPost(Name = "UpdateBoardGame")]
[ResponseCache(CacheProfileName = "NoCache")]
[SwaggerOperation(
    Summary = "Updates a board game.",
    Description = "Updates the board game's data.")]
public async Task<RestDTO<BoardGame?>> Post(BoardGameDTO model)

[Authorize(Roles = RoleNames.Administrator)]
[HttpDelete(Name = "DeleteBoardGame")]
[ResponseCache(CacheProfileName = "NoCache")]
[SwaggerOperation(
    Summary = "Deletes a board game.",
    Description = "Deletes a board game from the database.")]
public async Task<RestDTO<BoardGame?>> Delete(int id)
```

3. Use the `SwaggerParameter` attribute:

```csharp
public async Task<RestDTO<BoardGame[]>> Get(
    [FromQuery]
    [SwaggerParameter("A DTO object that can be used " +
        "to customize the data-retrieval parameters.")]
    RequestDTO<BoardGameDTO> input)
```

4. Enable annotations:

```csharp
builder.Services.AddSwaggerGen(options =>
{
    options.EnableAnnotations();  // Enables the Swashbuckle annotations feature
    // ... existing code
});
```

## Working with Minimal API

`[SwaggerOperation]` works on minimal API endpoints as well:

```csharp
using Swashbuckle.AspNetCore.Annotations;  // Required namespace

app.MapGet("/auth/test/1",
    [Authorize]
    [EnableCors("AnyOrigin")]
    [SwaggerOperation(
        Summary = "Auth test #1 (authenticated users).",
        Description = "Returns 200 - OK if called by " +
            "an authenticated user regardless of its role(s).")]
    [ResponseCache(NoStore = true)] () => { /* ... */ });

app.MapGet("/auth/test/2",
    [Authorize(Roles = RoleNames.Moderator)]
    [EnableCors("AnyOrigin")]
    [SwaggerOperation(
        Summary = "Auth test #2 (Moderator role).",
        Description = "Returns 200 - OK status code if called by " +
            "an authenticated user assigned to the Moderator role.")]
    [ResponseCache(NoStore = true)] () => { /* ... */ });

app.MapGet("/auth/test/3",
    [Authorize(Roles = RoleNames.Administrator)]
    [EnableCors("AnyOrigin")]
    [SwaggerOperation(
        Summary = "Auth test #3 (Administrator role).",
        Description = "Returns 200 - OK if called by " +
            "an authenticated user assigned to the Administrator role.")]
    [ResponseCache(NoStore = true)] () => { /* ... */ });
```

The Summary appears next to the endpoint in SwaggerUI; the Description appears when expanded.

## Describe responses

With XML comments — `<response>` tags map HTTP status codes to descriptions:

```csharp
/// <summary>
/// Performs a user login.
/// </summary>
/// <param name="input">A DTO containing the user's credentials.</param>
/// <returns>The Bearer Token (in JWT format).</returns>
/// <response code="200">User has been logged in</response>
/// <response code="400">Login failed (bad request)</response>
/// <response code="401">Login failed (unauthorized)</response>
```

With Swashbuckle — the `SwaggerResponse` attribute:

```csharp
app.MapGet("/auth/test/1",
    [Authorize]
    [EnableCors("AnyOrigin")]
    [SwaggerOperation(
        Summary = "Auth test #1 (authenticated users).",
        Description = "Returns 200 - OK if called by " +
            "an authenticated user regardless of its role(s).")]
    [SwaggerResponse(StatusCodes.Status200OK,
        "Authorized")]
    [SwaggerResponse(StatusCodes.Status401Unauthorized,
        "Not authorized")]
    /* ... */);
```

Both approaches populate the Responses table in SwaggerUI with code + description.

## Add request and response samples

- SwaggerUI takes care of it (most of the time) — e.g. an example-value JSON body is generated from the DTO schema
- It fails when there are multiple return types. We can add them with `ProducesResponseType`:

```csharp
[HttpPost]
[ResponseCache(CacheProfileName = "NoCache")]
[ProducesResponseType(typeof(string), 201)]
[ProducesResponseType(typeof(BadRequestObjectResult), 400)]
[ProducesResponseType(typeof(ProblemDetails), 500)]
```

## Group endpoints into sections

- SwaggerUI groups according to controllers. Inside the `swagger.json` file each path operation gets a `tags` array with the controller's name:

```json
{
  "openapi": "3.0.1",
  "info": { "title": "MyBGList", "version": "1.0" },
  "paths": {
    "/Account/Register": {
      "post": {
        "tags": [ "Account" ]
      }
    }
  }
}
```

- For minimal API and more configuration, edit your SwaggerOperations — add the `Tags` property:

```csharp
app.MapGet("/auth/test/1",
    [Authorize]
    [EnableCors("AnyOrigin")]
    [SwaggerOperation(
        Tags = new[] { "Auth" },
        /* ... */)]
    /* ... */);
```

This moves the endpoints from the default project group (e.g. "MyBGList") into a dedicated "Auth" section.

## Filter-based Swagger customization

Swashbuckle exposes a convenient filter pipeline that hooks into the `swagger.json` file-generation process, allowing us to create and add our own filters to customize the file's content:

- `IDocumentFilter` — to customize the whole swagger.json file
- `IOperationFilter` — to customize operations/endpoints
- `IParameterFilter` — to customize the operations' query string input parameters
- `IRequestBodyFilter` — to customize the operations' request body input parameters
- `ISchemaFilter` — to customize the input parameters' default schema

## Emphasizing the authorization requirements

The global `AddSecurityRequirement` call generates a padlock in SwaggerUI on **all** endpoints — even ones that don't need authorization:

```csharp
options.AddSecurityRequirement(new OpenApiSecurityRequirement
{
    {
        new OpenApiSecurityScheme
        {
            Name = "Bearer",
            In = ParameterLocation.Header,
            Reference = new OpenApiReference
            {
                Type = ReferenceType.SecurityScheme,
                Id = "Bearer"
            }
        },
        new string[] {}
    }
});
```

which in `swagger.json` produces on every operation:

```json
"security": [{
    "Bearer": [ ]
}]
```

We want a filter that sets the same security requirements, but only for operations with an `[Authorize]` attribute applied. Create a new class file inside the `/Swagger/` root-level folder:

```csharp
// /Swagger/AuthRequirementFilter.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.OpenApi.Models;
using Swashbuckle.AspNetCore.SwaggerGen;

namespace MyBGList.Swagger
{
    internal class AuthRequirementFilter : IOperationFilter
    {
        public void Apply(
            OpenApiOperation operation,
            OperationFilterContext context)
        {
            // Checks for the [Authorize] attribute — if not present, does nothing
            if (!context.ApiDescription
                .ActionDescriptor
                .EndpointMetadata
                .OfType<AuthorizeAttribute>()
                .Any())
                return;

            // If present, secures the operation
            operation.Security = new List<OpenApiSecurityRequirement>
            {
                new OpenApiSecurityRequirement
                {
                    {
                        new OpenApiSecurityScheme
                        {
                            Name = "Bearer",
                            In = ParameterLocation.Header,
                            Reference = new OpenApiReference
                            {
                                Type = ReferenceType.SecurityScheme,
                                Id = "Bearer"
                            }
                        },
                        new string[] {}
                    }
                }
            };
        }
    }
}
```

Update the AddSwaggerGen configuration in `Program.cs` — remove the previous global `AddSecurityRequirement` call and add the operation filter:

```csharp
using MyBGList.Swagger;  // Required namespace

// options.AddSecurityRequirement(...)  <-- previous code to remove

options.OperationFilter<AuthRequirementFilter>();  // New code to add
```

Now only the endpoints with `[Authorize]` show the padlock.

## Changing the application title

The application's title in SwaggerUI is by default set to the ASP.NET Core project name (e.g. MyBGList), per Swashbuckle's default behavior. Change it with an `IDocumentFilter`:

```csharp
// /Swagger/CustomDocumentFilter.cs
using Microsoft.AspNetCore.Authorization;
using Microsoft.OpenApi.Models;
using Swashbuckle.AspNetCore.SwaggerGen;

namespace MyBGList.Swagger
{
    internal class CustomDocumentFilter : IDocumentFilter
    {
        public void Apply(
            OpenApiDocument swaggerDoc,
            DocumentFilterContext context)
        {
            swaggerDoc.Info.Title = "MyBGList Web API";  // Sets a custom title
        }
    }
}
```

Register in `Program.cs`:

```csharp
options.OperationFilter<AuthRequirementFilter>();   // Existing filter
options.DocumentFilter<CustomDocumentFilter>();     // New filter
```
