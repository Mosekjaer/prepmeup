\section{Test Environment}
We run the tests in two places. Each test belongs to one of them, and the lists below say which.

\subsection{Local Run}
Most tests are run on the tester's own computer. The tester pulls the latest main, starts the system with docker compose (make up) and uses an Android emulator with the customer app in Expo Go. The administrator interface and Keycloak run in the same compose file. These tests check how the code behaves, and that is the same locally and on the server, because the containers are the same (appendix 7.3). The local run covers FR-01--06, FR-19, NFR-01--04, NFR-07 and NFR-09--11.

The result depends on the code, so the tester writes the commit that was tested next to the result, for example commit 1aca1c5. A container built before the latest pull can give another answer. NFR-04 gives 500 with an API image built before the error handling was merged, and 503 with the latest one.

\subsection{Run on the Server}
A local run does not show that the deployment works. We have one production environment and no test environment (appendix 7.3), and the system has behaved differently on the server before, when Keycloak started without our realm on Coolify (appendix 2.3). So the tester also runs these tests once before the deadline, against the deployed system from a device outside the server: NFR-05 and NFR-06, and a short check that a customer can sign in and sign up in the app installed from the latest EAS build, and that the administrator can sign in to the administrator interface in a browser. NFR-08 is checked in GitHub Actions and needs neither.

Customer A and customer B register through the customer app (FR-01) and get the household role. Administrator ADM is a user who has been given the admin role in the Keycloak admin console.

Some tests call the API directly, and they need an access token. The clients do not let you log in with a password from the command line. Instead the tester logs in through the administrator interface, opens the browser's developer tools and copies the Authorization header from a request to the API. A token is valid for 15 minutes.

The tests that call the API directly are kept as a Postman collection in the folder tests/acceptance in the repository. The collection contains no tokens or passwords, so it can be run again before the hand-in.

Tests that need orders with given dates use test data that is put into the database before the test. The data is described in the precondition of each test, and all dates are relative to the day the test is run.

NFR-03, NFR-04 and NFR-07 stop or start a single container. In the local run that is docker compose stop and start.

\section{Functional Requirements}
This section tests the must-have functional requirements in appendix 1.2, which are FR-01--06 and FR-19. Each test is a scenario that is run step by step against the deployed system. The actual result and the verdict are filled in when the test is run. The should-have and could-have requirements get tests when they are planned into a sprint.

\subsection{FR-01: Create account and subscription}
\scenarioinfo{FR-01}
  {Main scenario: A new customer creates an account, completes onboarding and signs up for a subscription.}
  {The customer app is installed on an Android device. The tester has an e-mail address that is not registered yet.}
  {The customer has an account, name and address are stored, and the customer has an active subscription with a planned order that contains the chosen packages.}
\begin{steps}
1 & The customer opens the app and taps Sign in. & The PrepMeUp login page of the identity provider opens, with a link to register. & The login page opened, with a link to register. & Pass \\
\hline
2 & The customer registers with the e-mail address and a password. & The app opens again and shows the onboarding screen, which asks for name and address. & The app opened again and showed the onboarding screen with name, phone, street, postal code and city. & Pass \\
\hline
3 & The customer saves onboarding with an empty name. & The details are not saved, and a message says that the name is missing. & Nothing was saved. The app said: Could not save your details. Check that your postal code has 4 digits and your phone number has 8 digits. It does not mention the name. & Fail \\
\hline
4 & The customer enters name and address and saves. & The app shows the home screen with the customer's name. & The home screen showed the name and the address. & Pass \\
\hline
5 & The customer chooses 2 adult packages and 1 child package and signs up for a subscription. & The app shows the subscription with status active and a planned order with 2 adult packages and 1 child package. & The home screen showed the subscription as active, with a planned order of 2 adult packages and 1 child package. & Pass \\
\hline
6 & The customer closes the app, opens it again and signs in. & The app does not show onboarding again. The subscription is still active, the planned order still has 2 adult packages and 1 child package, and name and address are the ones from step 4. & The app did not show onboarding. The subscription, the planned order and the customer details were the same. & Pass \\
\hline
\end{steps}

The test was run on 12-11-2026 against the system started locally with Docker (make up). The customer app ran in Expo Go on an Android emulator and not as an EAS build, and the tester closed the app with adb before step 6. A new e-mail address was registered for the test, so the customer had no subscription before step 5.

The test was run on 11-11-2026 against the system started locally with Docker (make up), with the calls made from the Postman collection. This is why the database is restarted first.

\subsection{FR-04: Expiry date of orders}
\scenarioinfo{FR-04}
  {Main scenario: The system registers an expiry date for each order when it is sent.}

  {Each sent order has its own expiry date.}
\begin{steps}

\hline
2 & The tester calls GET /subscription with A's token. & O1 has today's date as sent date and an expiry date exactly one year later. & The call answered 200. O1 had the sent date 25-11-2026 and the expiry date 25-11-2027. & Pass \\
\hline
3 & ADM marks O2 as sent. The tester calls GET /subscription with B's token and then with A's token. & O2 has its own expiry date. \hline
\end{steps}

The test was run on 25-11-2026 against the system started locally with Docker (make up) on commit 55fe2c0, with the calls made from the Postman collection. Customer A and customer B signed up in the customer app on an Android emulator in Expo Go, A with 2 adult packages and 1 child package and B with 1 adult package and 3 child packages. The tester signed in as an administrator, A and B in the order of the folders in the collection. The two expiry dates are exactly one year after the time each order was sent, so they differ by the minutes between the two orders being sent.
