\section{Glossary}

\textbf{Customer} = The person who has an account and a subscription

\textbf{Administrator} = An employee of PrepMeUp who maintains package types and dispatches orders through the administrator interface

\textbf{Subscription} = A customer's standing agreement to receive a new order before the previous one expires. Has a status (active, paused, cancelled).

\textbf{Order} = The packages a customer receives together in one shipment. The next order starts as a copy of the previous one, and the customer can change it while it is planned.

\textbf{Order status} = Whether an order is \emph{planned} (not yet sent, can be changed by the customer) or \emph{sent} (dispatched by the administrator). It follows from whether the order has a sent date. Delivery is not tracked.

\textbf{Package} = One package of a given package type in an order, with the price at the time the order was sent. A package is not tied to a specific person.

\textbf{Package type} = A package created by the administrator, e.g. \emph{Vegetarian -- Adult} or \emph{Vegetarian -- Child}. Adult and child versions are separate package types, and the name expresses the diet. Equipment, e.g. a flashlight, is offered as its own package type. A package type that has been ordered is never edited. To change the contents, the administrator creates a new package type, so past orders keep their contents.

\textbf{Package content} = One item and its quantity in a package type.

\textbf{Item} = A product that can go into a package. An item is either a \emph{food item} (including water) or an \emph{equipment item}.

\textbf{Expiry date} = The date on which the items of an order are no longer considered usable. The system schedules the next order before this date.

\textbf{Notification} = A message from the system to a customer, e.g. that a new order is about to be sent.

\section{System Description}
This system constitutes:
\begin{itemize}
    \item Back-end software
    \item A user interface for customers
    \item An administrator interface
\end{itemize}

Customers can sign up for a prepping subscription called ``PrepMeUp'' through the client app. The subscription ensures that they always have enough food and water for a three-day emergency.

\subsection{Platform}
The customer user interface is an Expo (React Native) app. Version 1.0 runs on Android; a web build of the same app is a could-have. The administrator interface is a web application.

\subsection{Payment}
Payment is simulated. The back-end records a payment for each order against the customer's stored (fake) card. A customer has one card. No real payment provider is integrated, and no real money is charged.

\subsection{Responsibilities}
The back-end part of the project is responsible for persistently storing information on:
\begin{itemize}
    \item All customers and their subscriptions
    \item The address of each customer
    \item The packages in each order and their package types
    \item The expiration date of the last order
\end{itemize}

The back-end is also responsible for:
\begin{itemize}
    \item Creating the next order shortly before the previous one expires
    \item Alerting the customer that they will soon receive a new order
    \item Alerting the administration that a new order is ready to be sent
\end{itemize}

The client part of the project provides a user interface for the customer, where they can sign up and compose their order from adult and child packages.

The administrator interface should make it possible to:
\begin{itemize}
    \item Add package types for the customers to choose between
    \item Replace a package type with a new version with different contents
    \item See which orders should be sent
\end{itemize}

\section{Epics and User Stories}
User stories are grouped into epics. Each epic lists the functional requirements (section~\ref{sec:fr}) that realise it.

\begin{enumerate}
    \item \textbf{Account} (FR-01, FR-08)
    \begin{enumerate}
        \item As a new customer, I want to be able to create an account, so that my user data, subscription, and orders are saved between sessions.
        \item As a customer, I want to log in with my e-mail and password, so that only I can see and change my orders.
        \item As a customer, I want to change my password, so that I can keep my account secure.
        \item As a customer, I want to delete my account, so that my personal data is removed when I no longer use the service.
    \end{enumerate}

    \item \textbf{Order contents} (FR-02, FR-08, FR-09, FR-13)
    \begin{enumerate}
        \item As a customer, I want to choose how many adult and child packages my order contains, so that my orders match the number of people I prepare for.
        \item As a customer, I want to choose the package type of each package, so that one person can get a vegetarian package and another a standard package.
        \item As a customer, I want to add equipment packages, e.g. a flashlight, to my order, so that I get more than food and water.
    \end{enumerate}

    \item \textbf{Subscription and orders} (FR-03, FR-04, FR-07, FR-10)
    \begin{enumerate}
        \item As a customer, I want to automatically receive a new order before the old one expires, so that I don't have to keep track of the expiration date myself and have a chance to use the soon-to-expire items.
        \item As a customer, I want to see the status of my next order, so that I know when to expect it.
        \item As a customer, I want to pause or cancel my subscription, so that I am not sent orders I do not need.
    \end{enumerate}

    \item \textbf{Notifications} (FR-04)
    \begin{enumerate}
        \item As a customer, I want to receive a notification shortly before my next order is sent, so that I have a chance to make changes (e.g. number of packages, package types).
    \end{enumerate}

    \item \textbf{Package catalogue} (FR-03, FR-11, FR-15)
    \begin{enumerate}
        \item As an administrator, I want to be able to add new types of packages, so that I can give customers more choices.
        \item As an administrator, I want to replace a package type with a new version with other items, so that I can keep the contents up to date without changing past orders.
    \end{enumerate}

    \item \textbf{Dispatch} (FR-05, FR-06)
    \begin{enumerate}
        \item As an administrator, I want to see the orders that should be sent, sorted by which order should be sent first.
        \item As an administrator, I want to mark an order as sent, so that the customer can see it is on its way.
    \end{enumerate}
\end{enumerate}

\section{Functional Requirements}
\label{sec:fr}
Functional requirements are numbered FR-\emph{nn}, non-functional requirements NFR-\emph{nn}, so the two can be told apart later in the report.

\paragraph{MUST HAVE}
\begin{enumerate}[label=\reqlabel{FR}, start=1]
    \item Customer UI: The customer can create an account and sign up for a PrepMeUp subscription.
    \item Back-end: Persistent storage of customers, their subscriptions and their orders.
    \item Back-end: Default package types for a ``normal'' diet, one for adults and one for children.
    \item Back-end: Keeps track of the expiration dates of the customer's past orders.
    \item Admin interface: See the next orders that should be sent.
    \item Admin interface: Register orders as sent.
\end{enumerate}

\paragraph{SHOULD HAVE}
\begin{enumerate}[label=\reqlabel{FR}, start=7]
    \item Customer UI: See the status of your orders and change a planned order.
    \item Customer UI: Change profile settings and address.
    \item Customer UI: Choose which package types an order contains, and how many of each.
    \item Back-end: A simulated card payment method.
    \item Admin interface: Create a package type.
\end{enumerate}

\paragraph{COULD HAVE}
\begin{enumerate}[label=\reqlabel{FR}, start=13]
    \item Customer UI: Add equipment packages, e.g. a flashlight, to an order.
    \item Back-end: A simulated card subscription method.
    \item Admin interface: Create a new version of a package type with other contents.
    \item Customer UI: Web build of the customer app.
\end{enumerate}

\paragraph{WON'T HAVE}
\begin{enumerate}[label=\reqlabel{FR}, start=12]
    \item Customer UI: Adjust the number of days the package lasts for. A customer who wants to cover more days orders more packages.
\end{enumerate}
\begin{enumerate}[label=\reqlabel{FR}, start=17]
    \item A custom package for each customer, depending on allergies.
    \item An integrated API to a real grocery supplier.
\end{enumerate}

\section{Scope and Delimitation}
We build the software side of the system. Hardware, logistics and the actual grocery supply are outside the project.

\subsection{Version 1.0 -- minimum viable product}
Version 1.0 is the smallest system that lets a customer subscribe and receive a first order. It contains:
\begin{itemize}
    \item An Android customer app (Expo, React Native) where a customer creates an account and signs up (FR-01).
    \item A back-end with persistent storage of customers, subscriptions and orders (FR-02).
    \item Default package types for a ``normal'' diet, one for adults and one for children (FR-03).
    \item Expiry tracking per order, so the next order can be scheduled (FR-04).
    \item An administrator interface that lists upcoming orders and lets the administrator mark them as sent (FR-05, FR-06).
    \item Simulated payment and simulated supplier.
\end{itemize}

\subsection{Out of scope}
\begin{itemize}
    \item Integration with a real grocery supplier or a real payment provider.
    \item iOS build of the customer app.
    \item Medicine and other prescription or regulated goods.
    \item Individually composed packages per customer based on allergies.
\end{itemize}

\section{Non-functional Requirements}
Each non-functional requirement is stated so it can be measured rather than judged. How each one is tested is described in appendix 6.1 (Acceptance Test).

\paragraph{Usability}
\begin{enumerate}[label=\reqlabel{NFR}, start=1]
    \item All text displayed in the UIs is in English, including error messages from the API.
    \item Every error message shown in a UI is a complete sentence in the UI language that states what went wrong and what the user can do about it. No stack traces, HTTP status codes or exception names are shown.
\end{enumerate}

\paragraph{Reliability}
\begin{enumerate}[label=\reqlabel{NFR}, start=3]
    \item If the back-end is unreachable, the customer app shows a connection error and keeps showing the last loaded data; it does not crash.
    \item If the database is unreachable, the API returns HTTP 503 with an error body instead of failing silently or crashing.
\end{enumerate}

\paragraph{Performance}
\begin{enumerate}[label=\reqlabel{NFR}, start=5]
    \item Response time is under 1 second for 90\% of requests.
\end{enumerate}

\paragraph{Portability}
\begin{enumerate}[label=\reqlabel{NFR}, start=6]
    \item The customer UI runs as an Android app built with Expo (React Native).
\end{enumerate}

\paragraph{Supportability}
\begin{enumerate}[label=\reqlabel{NFR}, start=7]
    \item The application refuses to start if a required configuration value is missing, instead of running with an incorrect default.
    \item Automated tests that cover all endpoints.
\end{enumerate}

\paragraph{Security}
\begin{enumerate}[label=\reqlabel{NFR}, start=9]
    \item A customer can only view and change their own data (subscription, orders, address). A request for another customer's data is rejected with HTTP 403.
    \item Endpoints reserved for administrators reject requests made with a customer's access token, with HTTP 403.
    \item Any endpoint that requires a logged-in user rejects a request without a valid access token, with HTTP 401.
\end{enumerate}
